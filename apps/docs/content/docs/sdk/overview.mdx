`@vhyxvoid/sdk` lets code call your tunnelled server. It has two clients that do the same job in different ways.

<Callout type="warn" title="Node.js only">
  The SDK runs on Node.js. It can't be bundled for a browser, and the WebSocket client takes your API key secret, which must never reach client-side code. In a browser, call the tunnel URL with `fetch`. Details are in [Limitations](/limitations#the-sdk-is-nodejs-only).
</Callout>

```bash
npm install @vhyxvoid/sdk
```

Both `import { createClient } from '@vhyxvoid/sdk'` and `require('@vhyxvoid/sdk')` work. This was checked against `@vhyxvoid/sdk@1.1.0` from npm.

## Which client to use

| | [`createClient`](/sdk/http-client) (HTTP) | [`TunnelClient`](/sdk/websocket-client) (WebSocket) |
| --- | --- | --- |
| How it works | A plain `fetch` to your tunnel URL, `https://<slug>--<label>.vhyxvoid.com` | One long-lived WebSocket to the hub; each call is signed with your API key |
| Credentials | None. It sends no VhyxVoid credentials at all | API key ID and secret |
| Setup | Your account slug, or a `baseUrl` | Hub URL, key ID and secret, and a `connect()` call |
| Good for | Almost everything: scripts, tests, server-to-server calls | A Node.js process that makes many calls and wants one persistent connection |

Start with `createClient`. Use `TunnelClient` only if you have a reason to keep a connection open.

<Callout type="info">
  The tunnel URL is public: anyone who knows it can call your server, and `createClient` adds no authentication of its own. Anything sensitive needs protecting in your own application. See [Limitations](/limitations#tunnel-urls-are-public).
</Callout>

## Configuration from the environment

`createClient` reads `VHYXVOID_ACCOUNT_SLUG`, `VHYXVOID_LABEL` and `VHYXVOID_HUB_DOMAIN` when you don't pass the matching option. `TunnelClient` reads nothing from the environment. See [Environment variables](/reference/environment-variables).
