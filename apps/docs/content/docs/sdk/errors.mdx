## What each client throws

| Client | Failure | What is thrown |
| --- | --- | --- |
| HTTP (`createClient`) | Your server (or the tunnel) answered with a non-2xx status | [`ClientError`](#clienterror), with the status and the response body |
| HTTP | No answer within `timeout` | A `TimeoutError` (`The operation was aborted due to timeout`). It is not a `ClientError` |
| HTTP | The tunnel host can't be reached (DNS, network) | The error `fetch` throws |
| WebSocket (`TunnelClient`) | The request was refused, failed or timed out | [`TunnelError`](#tunnelerror), or its subclass `TunnelTimeoutError` |
| WebSocket | `connect()` couldn't reach the hub | A plain `Error`: `Hub connection failed: …` |

Both `ClientError` and `TunnelError` extend `Error`, so `err.message` and `err.name` work as usual. Catch them with `instanceof`:

```ts
import { ClientError } from '@vhyxvoid/sdk'

try {
  await api.get('/orders/17')
} catch (err) {
  if (err instanceof ClientError) console.log(err.status, err.data)
  else throw err
}
```

Note that a `ClientError` can come from the tunnel itself rather than from your server: a `404`, `502`, `503` or `504` when the agent or your server can't be reached, a `401` or `403` from the tunnel's [access rules](/dashboard/tunnel-access), a `429` from the rate limit, or a `413` for a body over 10 MB. Its `data` then looks like `{ "error": "…", "status": 503, "tunnel": true }` (with a `code` for agent errors), and the response has an `x-vhyxvoid-error` header. The `tunnel: true` field is how you tell the two apart. A status from one of the tunnel's [traffic rules](/dashboard/traffic-rules) is an answer like any other, marked with an `x-vhyxvoid-rule` header. See [HTTP status codes](/reference/http-status-codes).

## Codes on a `TunnelError`

`TunnelError.code` is a string, and `retryable` says whether the same request might succeed if you send it again.

| Code | Meaning | Retryable |
| --- | --- | --- |
| `AGENT_NOT_FOUND` | Raised by the client when you haven't called `connect()`, and by the hub when no agent with your `label` is connected for your account. | No |
| `AGENT_TIMEOUT` | The hub or the client gave up waiting for an answer. Thrown as `TunnelTimeoutError`. | Yes |
| `AGENT_DISCONNECTED` | The hub connection closed while the request was waiting. | Yes |
| `BACKEND_UNAVAILABLE` | The agent couldn't get an answer from your local server: it isn't running on that port, or it didn't answer in time. | No |
| `PAYLOAD_TOO_LARGE` | The request body is over the 10 MB limit. | No |
| `INVALID_SIGNATURE` | The key ID is unknown, or the secret doesn't match it. | No |
| `AUTH_FAILED` | The request's timestamp is more than 30 seconds off the hub's clock, or the key isn't accepted. Check the clock on the machine running the SDK. | No |
| `SCOPE_MISSING` | The key lacks the `tunnel:connect` scope. | No |
| `INVALID_MESSAGE` | The request `path` doesn't start with a single `/` (for example, it is a full URL such as `http://…`). Pass a path on your own server, like `/api/orders`. | No |
| `REPLAY_ATTACK`, `EXPIRED_KEY`, `REVOKED_KEY`, `SUSPENDED_ACCOUNT` | The key was rejected: a request ID was reused, the key expired or was revoked, or the account isn't in a state that can connect. `SUSPENDED_ACCOUNT` no longer fires for an account in its seven-day payment grace period (fixed 2026-09-22) — only once it's actually suspended or worse. | No |
| `INTERNAL_ERROR` | Something went wrong in the hub while handling the request. Retrying later may work. | No |
| `RATE_LIMITED` | The key exceeded its per-minute limit. See [plans and limits](/reference/plans-and-limits#not-listed-here). | No |

The list is taken from what the hub's request path and the key validator can return, not from a promise about every future code. If you see one that isn't here, the `message` explains it.
