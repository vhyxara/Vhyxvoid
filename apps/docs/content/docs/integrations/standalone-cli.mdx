The `vhyxvoid` command runs the agent as its own process. It works with anything that listens on a local port: Django, Rails, Go, a static file server. Use it when there is no framework integration for your stack, or when you'd rather keep the tunnel out of your app's process. For Next.js, Express and Fastify there are [in-process integrations](/integrations/nextjs).

## Run it

You don't need to install anything:

```bash
npx @vhyxvoid/agent --key vhyxvoid_dev_xxxxxxxx --secret your-key-secret --port 3000
```

Or install it once, so `vhyxvoid` is available as a command:

```bash
npm install --save-dev @vhyxvoid/agent
npx vhyxvoid --port 3000
```

Creating an API key is covered in the [Quickstart](/getting-started/quickstart#1-create-an-account-and-an-api-key). When the agent connects it prints your public URL:

```text
  ✅  Tunnel active

  Local:   http://localhost:3000
  Public:  https://acme--default.vhyxvoid.com

  Share the Public URL — it is stable and never changes.
```

Stop it with Ctrl+C. If the connection to VhyxVoid drops it reconnects on its own.

## Keep credentials in a file, not on the command line

Flags end up in your shell history and process list. Put them in a file in the directory you run the command from. The agent reads `.env`, `.env.local` and `.env.vhyxvoid` from the current directory, in that order, and the later files win:

```bash title=".env.vhyxvoid"
VHYXVOID_API_KEY=vhyxvoid_dev_xxxxxxxx
VHYXVOID_SECRET=your-key-secret
VHYXVOID_PORT=3000
VHYXVOID_LABEL=web
```

Then just run `npx vhyxvoid`. Add `.env.vhyxvoid` to your `.gitignore`. A flag on the command line beats a value from a file; this was checked, with `--label` overriding `VHYXVOID_LABEL` from `.env.vhyxvoid`. Values in these files also take precedence over variables already set in your shell.

## Interactive setup

`vhyxvoid init` asks for your details and writes `.env.vhyxvoid` for you, and adds that file to `.gitignore` (creating it if needed):

```bash
npx @vhyxvoid/agent init
```

It asks for the key ID, the secret (shown as `*`), the port, the label, the hub URL and an optional account slug, the part of your tunnel URL before `--`. Blank answers take the defaults shown in brackets. Ctrl-C at any prompt cancels without writing anything, and a blank key or secret stops with an error. It also accepts answers piped in, one per line, for scripts.

## Commands and flags

`vhyxvoid` with no command is the same as `vhyxvoid start`. Every flag, its environment variable and its default are listed in the [CLI reference](/cli/reference), which is generated from the command itself. The ones you will use most are `--key`, `--secret`, `--port` and `--label`.

### Writing the URL to a file

`--write-env` saves your public URL where other tools can read it. With `--write-env`, the agent writes `NEXT_PUBLIC_TUNNEL_URL=https://…` into `.env.local` as soon as it connects, replacing an existing line with the same name. Give a file name and a different variable to change either:

```bash
npx vhyxvoid --write-env .env.development --env-key API_PUBLIC_URL
```

### Several tunnels

Each tunnel is one agent process with its own label and port, and its own URL:

```bash
npx vhyxvoid --label web --port 3000
npx vhyxvoid --label api --port 4000   # in another terminal
```

### The queue and local discovery

- **Queue.** The agent keeps a small SQLite file (`~/.vhyxvoid/queue.db` unless you set `--queue-path`) so that responses it could not send while disconnected can be sent after it reconnects. It needs the `better-sqlite3` native module; see [Installation](/getting-started/installation). Requests that arrive while the agent is disconnected are not replayed; see [Limitations](/limitations).
- **Local discovery.** By default the agent also listens on `127.0.0.1:4242` so that the [SDK](/sdk/overview), when it runs on the same machine, can find it. It answers only on your own machine, and has no authentication. If you don't use the SDK locally, pass `--no-local-discovery`. It is also the flag to reach for if port 4242 is already taken.

## Things to know

- **Response caching.** The agent keeps some `GET` responses in memory and can answer repeat requests without asking your server. It does this only when your server sends `Cache-Control` with a `max-age` above zero on a successful response. Entries are kept per caller: a cookie, an `Authorization` header, or a header whose name looks like a credential (`x-api-key`, `x-auth-token`, `x-csrf-token`, `x-session-id`, and similar) gives that caller their own entries, so two callers with different credentials never share one. Responses that set a cookie, or send `Vary: *`, are never cached, and a `Vary` header is honoured. A custom credential header with an unusual name is not recognised, so a server that authenticates that way should send `Vary` or `Cache-Control: no-store`. Cached responses carry `x-vhyxvoid-cache: HIT`. See [Limitations](/limitations#cached-responses).
- **Host header.** Your server sees `Host: 127.0.0.1:<port>` and `x-forwarded-host` set to the same, plus `x-forwarded-by: vhyxvoid`, not the public hostname.
- **Output.** The agent prints a version banner, a couple of `[agent]` status lines, and the tunnel details shown above. Use `--debug` for everything else.
- **Version.** `vhyxvoid --version` and the banner show the installed package's version. Releases before 1.0.19 showed `1.0.16` for 1.0.18.
