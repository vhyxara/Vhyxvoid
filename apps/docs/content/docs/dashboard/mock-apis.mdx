A mock API answers at `https://<slug>--<label>.vhyxvoid.com`, the same kind of URL as a tunnel, with no agent and no server of your own. Frontend developers, tests and webhook senders can use it before the backend exists. When the real backend is ready, start the agent on the **same label**: the URL stays the same and moves to your server, route by route.

## Create one

Open **Mock APIs** under a workspace and pick a starting point:

| Template | What you get |
| --- | --- |
| **Blank** | `GET /health` answering `{ "ok": true }`. |
| **REST resource** | List, read, create, update and delete users, with realistic fake data, a `404` for id `0` and a `422` when `email` is missing. |
| **Auth** | `POST /auth/login` that accepts the password `secret`, and `GET /me` that needs a bearer token. |
| **Errors and slowness** | A 3-second endpoint, one that fails every other call, and one that is always rate limited. |
| **Import a file** | Paste or upload an OpenAPI 3 or Swagger 2 document (JSON or YAML), a Postman collection, a Mockoon environment, a HAR file recorded in your browser, or a VhyxVoid export. The format is detected; see [Import](#import). |

Give it a name and a label (lowercase letters, digits and single hyphens). The mock answers as soon as it is created; the editor opens on it.

```bash
curl https://acme--users-api.vhyxvoid.com/users/7
# {"id":"7","name":"Grace Hopper","email":"ada.lovelace@example.com","city":"Lisbon"}
```

## Endpoints

Each endpoint has a method (or **ANY**) and a path:

- `/users/:id` or `/users/{id}` captures one segment as a parameter;
- `*` at the end matches the rest of the path (`/files/*`);
- a trailing slash doesn't matter, and the query string is not part of the path.

Endpoints are checked **from the top**; the first one that matches answers. Reorder them with the arrows, switch one off without deleting it, or duplicate it. A `GET` endpoint also answers `HEAD` (without a body).

## Responses

An endpoint can have several responses. **Which response answers** is one of:

- **First whose rules match, else the default.** Each response can have rules on a query parameter, header, path parameter, cookie, JSON body field (`user.email`, `items.0.sku`; empty means the whole body), the method or the path, tested with *equals*, *is not*, *contains*, *is present*, *is missing* or *matches regex*, all or any of them. When no response's rules match, the response marked **default** answers (or the first one without rules). The editor shows which one that is.
- **Each in turn**: the first call gets the first response, the next call the second, and so on. Handy for "fails every other time". The count starts over when you save.
- **One at random.**

Each response has a status, headers, a body and an optional extra delay. Hosted answers are capped at 256 KB per body before templating.

## Templating

Switch on **Templating** for a response to fill its body and header values from the request and from generators. Click a tag in the cheat sheet to insert it.

| Tag | Gives |
| --- | --- |
| `{{request.params.id}}`, `{{request.query.page}}`, `{{request.headers.authorization}}`, `{{request.cookies.sid}}` | Parts of the request |
| `{{request.body.user.email}}`, `{{json request.body}}` | A JSON body field, or the whole body as JSON |
| `{{request.method}}`, `{{request.path}}` | Method and path |
| `{{uuid}}`, `{{now}}`, `{{timestamp}}` | Random UUID, current time (ISO, or seconds) |
| `{{int 1 100}}`, `{{float 0 1 2}}`, `{{bool}}`, `{{pick 'a' 'b'}}` | Numbers, booleans, one of a list |
| `{{fullName}}`, `{{firstName}}`, `{{lastName}}`, `{{email}}`, `{{company}}`, `{{city}}`, `{{country}}`, `{{lorem 8}}` | Realistic fake data |
| `{{#repeat 5}}…{{/repeat}}`, `{{#repeat 2 10}}…{{/repeat}}`, `{{@index}}` | A block repeated (a fixed or random number of times), with its index |

A trailing comma inside `repeat` is dropped, so a list is easy to write:

```json
{ "data": [{{#repeat 3}}{ "id": "{{uuid}}", "name": "{{fullName}}" },{{/repeat}}] }
```

Templating runs no code: there are no expressions or conditions (use response rules for those), and a rendered answer is capped at 2 MB. A tag that doesn't exist is refused when you save; if a template still fails at request time, the mock answers `500` with the reason.

## Mock first, or only while offline

**Answers** decides how the mock shares its label with an agent:

- **Mock first (agent gets the rest).** The mock answers the routes it has, even while an agent is connected; everything else goes to the agent (with its body untouched), or gets `404` when no agent is running. Build a frontend against the mock, then replace endpoints one at a time as the backend implements them: delete the mocked route and the agent answers it.
- **Only while the agent is offline.** Your server answers while the agent runs; the mock takes over when it stops. A maintenance page or a stand-in for a laptop that is asleep.

A request to a mock's URL that matches no endpoint, with no agent running, gets `404` with `x-vhyxvoid-error: MOCK_NO_ROUTE` and a message naming the method and path.

## CORS and latency

**CORS for browsers** (on by default) answers preflight `OPTIONS` requests for any path and adds `Access-Control-Allow-*` headers to every answer, allowing the caller's origin with credentials. Switch it off to set CORS headers yourself.

**Latency for every answer** adds a delay to every response, on top of each response's own extra delay (up to 30 seconds in total per answer).

## Resources: a REST API with stored data

Add a **resource** (under the endpoints) and the mock gets a complete REST collection, with no endpoints to write. A resource called `users` at `/users` answers:

| Request | Does |
| --- | --- |
| `GET /users` | List. Filter on any field (`?role=admin`, `?address.city=Lisbon`), search all fields (`?q=ada`), sort (`?_sort=name&_order=desc`), page (`?_page=2&_limit=10`). The total is in the `X-Total-Count` header. |
| `POST /users` | Create from a JSON body. The id comes from the body, or is the next number (or a UUID when ids are text). Answers `201` with a `Location` header, `409` if the id exists. |
| `GET /users/:id` | Read, or `404`. |
| `PUT /users/:id` | Replace (the id stays). |
| `PATCH /users/:id` | Change the fields you send. |
| `DELETE /users/:id` | Delete (`204`). |

Data starts from the **seed** (a JSON list of objects you edit in the dashboard) and is kept between requests, for everyone who calls the URL. **Live data** shows what is stored now; **Reset to seed** puts it back, which you also need after changing the seed. A body that isn't a JSON object gets `400`. A resource holds up to 1,000 items of up to 64 KB each, and a mock has up to 20 resources. Data nobody wrote to for 30 days is dropped and starts again from the seed.

Endpoints come first: an endpoint for `GET /users/me` answers that path even though `/users` is a resource, so you can override any route by hand. **Try** answers resource routes from the live data, exactly like the URL (so a `POST` in Try really creates an item).

## Record from real traffic

Already have a working backend? Let it write the mock:

- **Record** (in the editor) lists the requests the [request inspector](/dashboard/request-inspector) captured on a tunnel. Pick the ones you want and they become endpoints with the real responses.
- **Add to a mock API** (on any request in the inspector) does the same for one request.

Ids in paths (numbers, UUIDs, long tokens such as `cus_NffrFeUfNV2Hib`) become parameters, so `/users/42` and `/users/43` become one `GET /users/:id` endpoint. When the same route answered with different statuses, each becomes a response, and the non-`2xx` ones get a rule on the id they were seen with (for example `404` only for id `99`). Only `Content-Type`, `Location`, `Cache-Control`, `Retry-After` and `WWW-Authenticate` response headers are kept, never cookies or credentials. Routes the mock already has are skipped. Requests answered by a mock or a traffic rule are not offered (they aren't your backend's answers).

## Import

**Import** (and **Import a file** when creating a mock) accepts, detected automatically:

| Format | What becomes what |
| --- | --- |
| OpenAPI 3 / Swagger 2 (JSON or YAML) | Each operation an endpoint; responses from `example`, the first of `examples`, or a sample built from the schema. |
| Postman collection (v2.0 / v2.1) | Each request an endpoint, its saved examples the responses; `{{baseUrl}}` and other variables in paths become parameters. |
| Mockoon environment | Routes, responses, rules (equals, regex, null, inverted), sequential and random modes, latency; CRUD routes with their data buckets become resources. Mockoon's own templating is kept as text. |
| HAR (from your browser's network tab) | Like **Record**: each request with its real response. |
| VhyxVoid export | Everything, including resources and settings. |

By default, routes and resources the mock already has are kept, so importing twice is harmless; **Replace all endpoints** starts over. Anything that could not be carried over is listed after the import.

## Export

**Export** downloads the saved mock as:

| Format | Use it for |
| --- | --- |
| OpenAPI (YAML or JSON) | Docs, code generators, Swagger UI. Response bodies become examples; the mock's URL is the server. |
| Mock Service Worker | A TypeScript file of [msw](https://mswjs.io) v2 handlers that behaves like the mock: rules (including body rules), each-in-turn and random responses, latency, and resources as in-memory collections. Use it in your frontend's dev mode or tests with `setupWorker(...handlers)` / `setupServer(...handlers)`. Templated bodies are sent as written. |
| Postman collection | Every endpoint as a request with its responses as saved examples, and a folder of requests per resource. |
| Mockoon | An environment for the Mockoon app or `@mockoon/cli`: rules, modes and latency carry over, resources become CRUD routes with data buckets, and the common template tags are translated. |
| VhyxVoid JSON | Everything, to back up, move to another workspace, or run offline. |

## Run it offline

Any JSON export runs on your machine with no account and no network, through the agent's [`vhyxvoid mock`](/cli/mock) command:

```bash
npx @vhyxvoid/agent mock ./users-api.vhyxvoid-mock.json --port 4010
```

## Try and see requests

- **Try** sends a request through the same engine the URL uses, including your unsaved changes, and shows which endpoint and response answered.
- **Requests** opens the [request inspector](/dashboard/request-inspector) for the mock's label: every call is captured there, marked ◇ with the endpoint (or resource) and response that answered.

## Saving

Changes are a draft until **Save** (or Ctrl+S / ⌘S); the page warns before you leave with unsaved changes. If someone else saved the same mock after you opened it, your save is refused with a message to reload, so nobody's work is overwritten. The new version answers at once.

## Things to know

- Mock answers count like any other request to your tunnel URLs: the per-minute limit, monthly usage, [traffic charts](/dashboard/tunnels#traffic) and [alerts](/dashboard/alerts) all include them.
- If the data store is briefly unavailable, resource routes answer `503` with `x-vhyxvoid-error: MOCK_STORE_UNAVAILABLE`; endpoints keep answering.
- [Tunnel access rules](/dashboard/tunnel-access) on the same label protect the mock too, and [traffic rules](/dashboard/traffic-rules) run before it (a traffic rule can still inject an error or add headers to mocked answers). The [webhook inbox](/dashboard/webhook-inbox) only stores requests the mock doesn't answer.
- A [custom domain](/dashboard/custom-domains) pointed at the label serves the mock as well.
- How many mock APIs a workspace can have, and how many endpoints each, depends on the plan (see [Plans and limits](/reference/plans-and-limits)). Mocks that exist keep answering after a downgrade.
- Owners and admins create and change mocks; every member can open them and use **Try**. Changes appear on the workspace's [Activity](/dashboard/activity) page.
