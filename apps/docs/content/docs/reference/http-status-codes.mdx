A request to `https://<slug>--<label>.vhyxvoid.com` (or to one of your [custom domains](/dashboard/custom-domains)) is answered by your server, or by VhyxVoid when it can't reach your server or a rule of yours answers instead. Anything your server returns, including its own `404` or `500`, passes through unchanged. The statuses below are the ones VhyxVoid itself produces.

When VhyxVoid answers, the body is JSON of this shape, and the response carries an `x-vhyxvoid-error` header with a short code. That is how you tell it from a reply of your own:

```json
{ "error": "The service behind this tunnel is not reachable right now.", "status": 502, "tunnel": true, "code": "BACKEND_UNAVAILABLE" }
```

| Status | Message (`error`) | Meaning and what to do |
| --- | --- | --- |
| `400` | `Invalid tunnel URL. Expected format: accountslug--label.vhyxvoid.com` | The hostname isn't `<account slug>--<label>.<domain>`. Check the URL the agent printed. |
| `400` | `Invalid request path` | The request target isn't a path starting with a single `/` (for example, a full URL in the request line). Browsers and normal HTTP clients never send this. |
| `401` | `This tunnel is password protected.` | The tunnel has a [password](/dashboard/tunnel-access). Browsers show a sign-in prompt (the response has `WWW-Authenticate: Basic`); other clients send the password as HTTP Basic auth, any user name. |
| `403` | `This tunnel only accepts requests from allowed IP addresses.` | The tunnel has an IP allowlist and the caller's address isn't on it. |
| `403` | `Access rules for this tunnel could not be checked. Try again shortly.` | VhyxVoid could not read the tunnel's access rules, so it refused rather than risk letting the request through. Retry. |
| `404` | `No active tunnel found for "<host>". If this is your tunnel, start the agent with label "<label>".` | Nothing is connected under this slug and label (code `TUNNEL_OFFLINE`). Start the agent, and check the label. A `404` **without** `"tunnel": true` came from your own server. |
| `404` | `No tunnel is connected to <host>.` | A custom domain that isn't verified, or isn't set up on VhyxVoid at all (code `UNKNOWN_DOMAIN`). See [Custom domains](/dashboard/custom-domains). |
| `404` | `No mock endpoint matches <METHOD> <path>. …` | The label is a [mock API](/dashboard/mock-apis), no agent is running, and none of its endpoints matches (code `MOCK_NO_ROUTE`). Add the endpoint, or start the agent. |
| `413` | `Request body too large. Maximum is 10MB` | The request body is over 10 MB. |
| `429` | `Rate limit exceeded: <n> requests/min for this account's plan` | Your account's tunnel URLs got more requests than your plan allows in one minute (FREE 100, PRO 3,000, ENTERPRISE unlimited; see [Plans and limits](/reference/plans-and-limits)), combined across every agent/label the account has. This is separate from the SDK's own per-key `RATE_LIMITED` error: a tunnel URL has no API key to check. The response includes a `Retry-After` header (seconds) and the same number as `retryAfterSeconds` in the JSON body. |
| `429` | `Too many wrong passwords. Try again shortly.` | More than 10 wrong tunnel passwords from one IP address in a minute. Wait for the `Retry-After` seconds. |
| `502` | `The service behind this tunnel is not reachable right now.` | The agent is connected, but your server didn't answer it: it isn't running on that port, refused the connection, or was too slow (code `BACKEND_UNAVAILABLE`). The agent's own output, or `--debug`, has the detail (the port and the error); it is not sent to the caller. |
| `502` | `The tunnel agent disconnected while handling this request. Try again.` | The agent lost its connection to VhyxVoid while your request was in flight (code `AGENT_DISCONNECTED`). Retry it, after checking the agent is running. |
| `502` | `The request could not be delivered to the tunnel agent. Try again.` | The hub couldn't hand the request to the agent (code `SEND_FAILED`). Retry. |
| `503` | `Tunnel is registered but agent is not connected. …` | The label is known but the agent isn't connected right now, for instance while it reconnects. Restart it if it stays down. |
| `503` | `The tunnel is offline and its inbox is full. Try again later.` | The tunnel's [webhook inbox](/dashboard/webhook-inbox) already holds as many requests as your plan allows. Has a `Retry-After` header, so webhook providers retry later. |
| `504` | `The service behind this tunnel did not respond in time.` | Nobody answered within the hub's request timeout (120 seconds by default; code `AGENT_TIMEOUT`). A slow server usually gives the `502` above first. |

Two answers that are not errors:

- **`202 Accepted`** with an `x-vhyxvoid-inbox` header: the tunnel was offline, its [webhook inbox](/dashboard/webhook-inbox) is on, and the request (`POST`, `PUT`, `PATCH` or `DELETE`) was stored to be delivered when the agent reconnects. Bodies over 1 MB get `413` instead.
- **Any status with an `x-vhyxvoid-mock` header**: the label's [mock API](/dashboard/mock-apis) answered; the header names the endpoint.
- **Any status with an `x-vhyxvoid-rule` header**: one of the tunnel's [traffic rules](/dashboard/traffic-rules) answered (a mock, an injected error or a redirect). The header names the rule.

`OPTIONS` requests (CORS preflights) are forwarded to your server like any other request, and your server's CORS headers, `Vary` and `Set-Cookie` reach the caller unchanged. VhyxVoid adds no CORS headers of its own and doesn't rewrite cookies, so cross-origin browser calls to a tunnel work only if your server allows them. Changed 2026-09-24 and not deployed yet: until then the hub answers `OPTIONS` itself with `204` and CORS headers allowing the request's own `Origin` with credentials, replaces your server's CORS headers the same way, and rewrites every cookie to `Domain=.vhyxvoid.com; SameSite=None; Secure`.

Requests that were in flight when an agent dropped are not replayed afterwards, and requests that arrive while it is down get the `404` or `503` above unless the webhook inbox is on; see [Limitations](/limitations#requests-dont-survive-agent-disconnects). For symptoms and fixes see [Troubleshooting](/troubleshooting).

## Timing

The hub's default request timeout is 120 seconds and can be set anywhere from 5 to 600 seconds by whoever operates the hub, with `TUNNEL_REQUEST_TIMEOUT_MS`. It is not something you can change. The agent stops waiting for your server slightly earlier than the hub does (two seconds earlier with agent 1.0.20 and later; a fixed 28 seconds for 1.0.19 and earlier, so a slow handler fails there first). See [Environment variables](/reference/environment-variables#tunnel-request-timeout).
