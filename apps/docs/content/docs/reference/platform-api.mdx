The dashboard's own API also accepts an **API key** on most of its routes. That is how the [CLI's platform commands](/cli/platform), the [GitHub Actions](/integrations/github-actions) and the [VS Code extension](/integrations/vscode) work, and you can call it from your own scripts too.

## Authenticate

Send the key ID and the secret, joined by a dot, as a bearer token:

```sh
curl https://api.vhyxvoid.com/api/v1/platform/whoami \
  -H "Authorization: Bearer $VHYXVOID_KEY_ID.$VHYXVOID_SECRET"
```

```json
{
  "success": true,
  "data": {
    "accountId": "5f1d…",
    "workspace": "Acme",
    "slug": "acme",
    "keyId": "vhyxvoid_dev_…",
    "scopes": ["specs:read", "specs:write"],
    "dashboardUrl": "https://www.vhyxvoid.com/organizations/5f1d…"
  }
}
```

`whoami` works with any valid key. Other routes need the right scope.

## What a key can do

A key acts in its own workspace only, **as the member who created it**: issues it opens, messages it posts and versions it publishes show that member's name. The key stops working when that member leaves the workspace, as well as when it is revoked or expires. After a [rotation](/dashboard/api-keys) the old secret keeps working until the grace period ends.

Each route that accepts a key names one scope:

| Scope | Routes |
| --- | --- |
| `mocks:read`, `mocks:write` | `/api/v1/mocks/:accountId/…`: list, read, export and try mocks; create, change, import into and delete them |
| `specs:read`, `specs:write` | `/api/v1/specs/:accountId/…`: read specs, versions and diffs, check a document (`POST …/:id/preview`); create, save drafts, publish. Also API drift: `POST /api/v1/analytics/:accountId/drift` |
| `collections:read`, `tests:run` | `/api/v1/api-client/:accountId/…`: read collections and runs; create, save, parse a file into a collection, run |
| `team:read`, `team:write` | `/api/v1/team/:accountId/…`: channels, messages, search, documents, issues, comments |
| `ai:use` | `/api/v1/ai/:accountId/…`: [AI assist](/dashboard/ai-assist) drafts (see below) |

The full list, with what each scope covers, is on [API key scopes](/reference/scopes). A key with `*` passes every scope check. Your plan limits how many scopes one key can carry; see [Plans and limits](/reference/plans-and-limits).

These stay **dashboard only**: managing members, keys, billing and settings, sharing API docs and their domains, deleting specs, collections and team content, environments, request history, recording mocks from traffic, and the request inspector. A key sent to one of them gets `401 This endpoint needs a dashboard sign-in, not an API key`.

## Errors

| Status | Meaning |
| --- | --- |
| `401` | The key is wrong, revoked, expired or past its rotation grace; or the route is dashboard only. |
| `403` | The key lacks the route's scope (the message names it), or the URL is for another workspace, or the key's creator is no longer a member. |
| `402` | A plan limit was reached; the message says which. |
| `429` | The key's requests-per-minute limit, or the per-address limit, was reached. Retry after the `Retry-After` header (see [Rate limits](#rate-limits)). |

Responses use the same `{ success, message, data }` envelope as the dashboard; errors add a `code` and a `requestId`. Each successful call updates the key's **Last used** time (at most once a minute).

## OpenAPI document

The platform API is described by an OpenAPI 3.1 document:

- **Live:** `https://api.vhyxvoid.com/api/v1/platform/openapi.json`. Fetching it needs no key.
- **In these docs:** [platform-api.openapi.json](https://www.vhyxvoid.com/docs/platform-api.openapi.json), the same document for this version of the docs.

It is generated from the routes the API serves, so it lists exactly the routes that accept a key. For each one it gives:
- the scope it needs (also as `x-required-scope`);
- the path and query parameters;
- the JSON schema of the request body, the same schema the API validates with;
- the success status, and the error and rate-limit responses.

Response bodies are described in each operation's description rather than as schemas.

Use it to:
- generate a client in your language;
- import it into Postman or Insomnia;
- import it into the [API client](/dashboard/api-client) as a collection of requests, or into a [mock API](/dashboard/mock-apis) to test against.

```sh
curl -s https://api.vhyxvoid.com/api/v1/platform/openapi.json -o vhyxvoid-platform.json
npx @openapitools/openapi-generator-cli generate -i vhyxvoid-platform.json -g typescript-fetch -o ./vhyxvoid-client
```

## Rate limits

Each API key may make a number of requests per clock minute, set by your plan:

| Plan | Requests per key per minute |
| --- | --- |
| Free | 120 |
| Pro | 1,200 |
| Enterprise | 6,000 |

Every response to a key carries:

| Header | |
| --- | --- |
| `X-RateLimit-Limit` | the key's limit per minute |
| `X-RateLimit-Remaining` | requests left this minute |
| `X-RateLimit-Reset` | seconds until the minute ends |

Over the limit, the API answers `429` with `Retry-After` (seconds until the next minute). Other keys of the workspace, and dashboard sign-ins, are not affected. Only requests with a valid key count, so nobody can use up your key's allowance by sending its key ID with a wrong secret. Each request also counts against a per-address limit, as it does from the dashboard.

The CLI, the GitHub Actions and the VS Code extension wait for `Retry-After` and try again, up to three times. They also poll background runs and drafts every second at first, then every 3 seconds, so a normal CI job stays well under the limit. To raise a key's limit, upgrade the plan; for many parallel jobs, give each its own key.

## Examples

Check a spec file against the latest published version, as `vhyxvoid spec check` does:

```sh
AUTH="Authorization: Bearer $VHYXVOID_KEY_ID.$VHYXVOID_SECRET"
API=https://api.vhyxvoid.com/api/v1
ACC=$(curl -s $API/platform/whoami -H "$AUTH" | jq -r .data.accountId)
SPEC=$(curl -s $API/specs/$ACC -H "$AUTH" | jq -r '.data.specs[] | select(.slug=="shop-api") | .id')
jq -Rs '{text: .}' openapi.yaml \
  | curl -s -X POST $API/specs/$ACC/$SPEC/preview -H "$AUTH" -H 'content-type: application/json' -d @- \
  | jq '.data.counts'
```

Run a stored collection and fail the script when a check fails. A run can take up to two minutes, so it runs in the background: the POST answers `202` with the run's id at once, and `GET /api-client/:accountId/runs/:runId` returns `"status": "running"` until it is `"done"` (with the `report`) or `"failed"` (with an `error`). This needs `tests:run` to start and `collections:read` to read the result.

```sh
RUN=$(curl -s -X POST $API/api-client/$ACC/collections/$COLLECTION/run -H "$AUTH" \
  -H 'content-type: application/json' -d '{"environmentId": "'$ENV'"}' | jq -r .data.id)
while :; do
  R=$(curl -s $API/api-client/$ACC/runs/$RUN -H "$AUTH")
  [ "$(echo "$R" | jq -r .data.status)" != running ] && break
  sleep 2
done
echo "$R" | jq -e '.data.status == "done" and .data.report.failed == 0 and .data.report.errored == 0'
```

Runs started with a key are stored like any other run and appear in the collection's run history in the dashboard, marked as running until they end. [`vhyxvoid test --collection`](/cli/platform#test---collection-nameid) does this polling for you.

## AI drafts

A draft can take a minute or two, longer than a proxy waits for one response, so it runs in the background:

1. `POST /api/v1/ai/:accountId/mock` with `{ "description": "…" }` (or `"trafficLabel"`), or `POST /api/v1/ai/:accountId/tests` with `{ "description", "specId", "trafficLabel", "baseUrl" }`, answers `202` with `{ "id": "…", "status": "running" }`.
2. `GET /api/v1/ai/:accountId/drafts/:id` returns `"status": "running"` until it is `"done"`, with the draft in `result`, or `"failed"`, with `error.message` and the `error.statusCode` it would have had. Poll every couple of seconds.

A draft can be read for 15 minutes, by the member (or that member's keys) who started it. `GET /api/v1/ai/:accountId` returns whether AI assist is available and how many drafts are left this month.
