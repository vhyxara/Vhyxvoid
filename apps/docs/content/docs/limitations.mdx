## Requests don't survive agent disconnects

If your agent loses its connection to VhyxVoid and a request arrives before it reconnects, that request is not held and replayed afterwards. The caller gets an error instead: a `503` if the hub already knows the agent is gone, or a `502` or `504` if the connection dropped while the request was in flight.

- **`GET` and other safe requests:** retrying is fine.
- **`POST`, `PUT`, `PATCH`, `DELETE`:** a request that was already handed to your server can still be processed after the caller has been told it failed. Retrying may apply the change twice. Make these handlers idempotent (for example with an idempotency key) if a duplicate would cause harm.

## Tunnel URLs are public

Anyone who knows or guesses a tunnel URL can send requests to your local server. VhyxVoid does not authenticate callers on the tunnel URL, and the SDK's HTTP client sends no credentials. Don't tunnel a server that holds real data, and protect anything sensitive in your own application. There is a per-account rate limit on this path (see [Plans and limits](/reference/plans-and-limits)), but it exists to catch abuse, not to authenticate or authorize a caller.

## The SDK is Node.js only

<Callout type="warn" title="Not usable in a browser">
  `@vhyxvoid/sdk` runs on Node.js. It cannot be bundled for a browser, and it should not be.
</Callout>

An earlier version of this page, and other descriptions of the SDK, called the WebSocket client browser-oriented. That was wrong, and it is corrected here.

- **It cannot be bundled.** The SDK uses Node's built-in `crypto` module (to sign requests) and `http` module (to find a local agent). Bundling it for a browser fails with `Could not resolve "crypto"` and `Could not resolve "http"`, and that is true even if you import only `createClient`. This was checked against the published 1.1.0 with esbuild.
- **Making it bundle would not make it safe.** `TunnelClient`, the WebSocket client, authenticates with your API key ID and secret. Any browser bundle that contains them hands them to everyone who loads the page. Running it in browsers needs a different way of authenticating, not just a bundler setting, and that is not planned for this release.
- **In a browser, call your tunnel URL directly.** It is a public URL that needs no key, so plain `fetch` works. Don't put an API key or secret in client-side code.
- **What `TunnelClient` is for.** A Node.js process that wants one persistent WebSocket connection to the hub instead of a new HTTPS request per call. Keep its key ID and secret on the server, in environment variables. The HTTP client (`createClient`) is the default choice and needs no key at all.

## WebSockets through a tunnel are partial

A WebSocket connection to a tunnel URL is carried to your server, and a simple connection that sends and receives a few messages works. It is **not yet reliable** for the tools that rely on it:

- Vite hot reload fails, because the relay doesn't handle WebSocket subprotocols. The browser sees the connection close with code `1011`.
- A message sent right after the connection opens can be lost, which makes socket.io fall back to long polling.
- There is no cap on connections and no keep-alive.

`@vhyxvoid/agent` 1.0.20 (and `@vhyxvoid/next` and `@vhyxvoid/middleware` 1.0.5) fixed messages lost or reordered in bursts, messages arriving after a close, sockets left open after a disconnect and unsendable close codes. Those fixes come in two halves, one in the agent and one in the hub, and this page can't tell you which hub you are talking to. The two problems above are not fixed. Hot reload for Next.js and other frameworks over a tunnel hasn't been tested. A tunnelled WebSocket is exactly as public as the tunnel URL itself. The symptoms and workarounds are on [Troubleshooting](/troubleshooting#websockets-and-hot-reload-through-a-tunnel).

## Cached responses

The agent keeps some `GET` responses in memory and can answer repeat requests without asking your server. It does this only when your server's response is a `2xx` with a `Cache-Control` header whose `max-age` is above zero, and it marks responses with an `x-vhyxvoid-cache: HIT` or `MISS` header.

- **Per caller.** Entries are keyed by path and query string and by the caller's credentials: cookies, `Authorization`, and headers whose names look like credentials (`x-api-key`, `x-auth-token`, `x-csrf-token`, `x-session-id`, and similar). Two callers with different credentials never share an entry, and an anonymous response is never given to a credentialed caller.
- **Never cached:** responses that set a cookie, or send `Vary: *`. A `Vary` header is honoured for the request headers it names.
- **What is not covered:** a custom credential header whose name matches none of those patterns. If your server authenticates that way, send `Vary` or `Cache-Control: no-store`.
- **Older agents.** In `@vhyxvoid/agent` 1.0.18 and earlier the cache ignored credentials, so a response produced for one user could be handed to another. Upgrade to 1.0.19 or later. The in-process integrations bundle the agent, so upgrade `@vhyxvoid/next` and `@vhyxvoid/middleware` to 1.0.4 or later too.

## Your server sees a local Host header

Requests reach your server with `Host` (and `x-forwarded-host`) set to `127.0.0.1:<port>`, not the public hostname, and with `x-forwarded-by: vhyxvoid`. Code that builds absolute URLs from those headers, or signs the request host, will not see your tunnel URL.

## Request size and time

- Request bodies are limited to **10 MB**. Larger requests get `413`.
- The hub waits **120 seconds** by default for an answer (whoever operates the hub can set 5 to 600 seconds), and `@vhyxvoid/agent` 1.0.20 and later wait for your server for as long as the hub allows, minus two seconds (118 seconds on the default). `@vhyxvoid/agent` 1.0.19 and earlier stop waiting after **28 seconds**, and the caller then gets `502`. The in-process integrations bundle the agent, so `@vhyxvoid/next` and `@vhyxvoid/middleware` need 1.0.5 or later for the same. See [Environment variables](/reference/environment-variables#tunnel-request-timeout).
