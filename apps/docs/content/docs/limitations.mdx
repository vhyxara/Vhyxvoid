## Requests don't survive agent disconnects

If your agent loses its connection to VhyxVoid and a request arrives before it reconnects, that request is not held and replayed afterwards. The caller gets a `504` after the 30 second timeout.

- **`GET` and other safe requests:** retrying is fine.
- **`POST`, `PUT`, `PATCH`, `DELETE`:** a request that was already handed to your server can still be processed after the caller has been told it failed. Retrying may apply the change twice. Make these handlers idempotent (for example with an idempotency key) if a duplicate would cause harm.

## Tunnel URLs are public

Anyone who knows or guesses a tunnel URL can send requests to your local server. VhyxVoid does not authenticate callers on the tunnel URL, and the SDK's HTTP client sends no credentials. Don't tunnel a server that holds real data, and protect anything sensitive in your own application.

## Cached responses can be shared between callers

The agent keeps some `GET` responses in memory and can answer repeat requests without asking your server. It does this only when your server's response is a `2xx` with a `Cache-Control` header whose `max-age` is above zero. Entries are keyed by path and query string alone, not by cookies or `Authorization`, so a response your server produced for one user can be returned to another until it expires. This was reproduced with two requests carrying different cookies. Responses are marked with an `x-vhyxvoid-cache: HIT` or `MISS` header. If your dev server sends `max-age` on personalised pages, send `Cache-Control: no-store` on them while you tunnel. The source now keys the cache on the caller's credentials as well, but that is not published yet, so this describes the released agent.

## Your server sees a local Host header

Requests reach your server with `Host` (and `x-forwarded-host`) set to `127.0.0.1:<port>`, not the public hostname, and with `x-forwarded-by: vhyxvoid`. Code that builds absolute URLs from those headers, or signs the request host, will not see your tunnel URL.

## Request size and time

- Request bodies are limited to **10 MB**. Larger requests get `413`.
- Your server has **30 seconds** to respond. After that the caller gets `504`.

## The WebSocket client exposes your secret to the browser

`TunnelClient`, the SDK's WebSocket client, is configured with your API key secret. If you use it in browser code, that secret is in your JavaScript bundle. If you must, use a dedicated DEV key with only the scopes it needs, and never a production key. The HTTP client (`createClient`) doesn't have this problem, because it uses no key.

## Known problems in the current releases

These are bugs in the published packages, not design limits, and each will be removed from this list when a fixed version is published. All of them are already fixed in the source; none of the fixes has been published yet.

- **`@vhyxvoid/middleware` 1.0.3 crashes at startup** when credentials are set, with `Could not locate the bindings file`. See [Express](/integrations/express). Use the [CLI](/integrations/standalone-cli) instead.
- **`@vhyxvoid/next` 1.0.3 and `@vhyxvoid/middleware` 1.0.3 don't declare `better-sqlite3`,** which they need. Install it yourself. See [Next.js](/integrations/nextjs).
- **`vhyxvoid init` exits early** without writing your credentials file (`@vhyxvoid/agent` 1.0.18, Node 24). See the [CLI page](/integrations/standalone-cli).
- **`vhyxvoid --version` and the startup banner say `1.0.16`** for the 1.0.18 package.
- **The agent prints verbose `[agent]` and `[batcher]` debug lines.**

### `@vhyxvoid/sdk` 1.0.1 can't be `import`ed

The package declares an ES module entry point that was never built, so `import … from '@vhyxvoid/sdk'` fails. Use `require()`, or `createRequire` from an ES module. See the [Quickstart](/getting-started/quickstart).
