### 2026-09-17 — Scoping session: app location/naming/port, VhyxUI-from-day-1, separate auth wiring, copy not extract, revised screen list

**Decided by:** Claude Code (investigation-and-plan session, no code written)
**Context:** First-ever session scoping a real frontend for `apps/api`'s complete, working, never-consumed Admin RBAC backend. Brief asked for investigation and a concrete plan, explicitly no scaffolding this session.

**Location/naming — decided:** `apps/admin`, package `@vhyxvoid/admin`, matching `apps/web`'s `@vhyxvoid/web` convention exactly. No alternative naming seriously considered — the monorepo's existing `apps/*` pattern (`web`, `api`, `hub`, `demo-backend`) makes `admin` the obvious, unambiguous choice.

**Excluded from root `tsconfig.json`'s project-reference graph, own ESLint config — decided:** matches `apps/web`'s established precedent exactly (see `internal-tools/user-frontend/context.md`'s Tech Stack section and its own decision.md for why apps/web was excluded originally). No new rationale needed — this is "do what the only existing Next.js app in the monorepo already does," not a fresh judgment call.

**Port — decided:** 4001. `apps/web` occupies 4000 (with 4177 as an established local fallback already wired into `apps/api`'s CORS `allowedOrigins`), `apps/api` = 9000, `apps/hub` = 9001. 4001 is unused today and keeps `apps/admin` visually/mentally paired with `apps/web`'s 4000 without colliding with either of apps/web's two known ports. **Not implemented this session** — no `allowedOrigins` edit made, since the app doesn't exist yet; flagged in backlog.md for the scaffolding session.

**VhyxUI + `@vhyx/api-kit` adoption from day one — confirmed, not re-litigated.** Both sibling-repo `link:` conventions were already explicitly generalized ("the established pattern for any future workspace," `internal-tools/shared/context.md`) and `@vhyx/api-kit`'s `createHttpClient` was already deliberately built configurable (injected `getAuthHeaders`/`onUnauthorized`) specifically so a second, differently-authenticated consumer wouldn't need its own fork — this session just confirmed that design intent actually holds for the admin app's genuinely-different auth shape (see next entry) rather than assuming it. No MUI phase — nothing about the Admin RBAC backend or VhyxUI's current component set implies needing MUI as a bridge the way apps/web's Vuexy-template history did.

**Auth wiring — the one real "don't assume" investigation this session did.** The brief's premise (`AdminSession` is genuinely separate from apps/web's regular-user auth) was already documented in `internal-tools/api/context.md`, but "separate system" could have meant anything from "different DB table, same everything else" to "nothing shareable at all." Investigated directly by reading `AdminLogin.usecase.ts`, `adminAuthGuard.plugin.ts`, `identity.routes.ts`'s login handler, and `userAuthGuard.ts`. **Found two things, one confirming the premise and one contradicting a different, previously-undocumented assumption:**
1. **Confirmed separate, concretely:** admin login returns `accessToken`+`refreshToken` in the JSON body with zero cookie involvement (grepped the whole admin module for `cookie`/`Cookie`: zero hits); regular-user login sets the refresh token as an httpOnly cookie. This is a real, load-bearing difference — `apps/admin` cannot lift `apps/web`'s httpClient/refresh-interceptor code wholesale, it needs its own token-storage and refresh-retry wiring (in-memory access token + an explicit refresh call via `@vhyx/api-kit`'s `onUnauthorized` hook, not `localStorage` for the refresh token — avoiding the exact XSS-exposure class `internal-tools/user-frontend/context.md` item 42 already removed from apps/web's own code).
2. **New finding, corrects a *different*, previously-wrong cross-cutting claim:** `internal-tools/shared/context.md`'s Configuration table said `PRIVATE_KEY`/`PUBLIC_KEY` (RS256) were dead and `JWT_SECRET` (`@fastify/jwt`, HS256) was "what's actually live." Reading `AdminLogin.usecase.ts` (which constructs `RS256JwtService` directly) and tracing its registration (`core.plugin.ts`) found the opposite: RS256 is the real, live signer for **both** admin and regular-user tokens; `@fastify/jwt`/`JWT_SECRET` is registered but its only consumer (`core/middleware/auth.middleware.ts`'s `authenticate`) is already-known dead code. This doesn't change the admin/user auth-separation conclusion (the *guards* and *token payloads* are still fully separate — different `type` field, different DB session table, different route trees) but it does mean the two systems share the same underlying RS256 key material, worth knowing if key rotation is ever planned (rotating `PRIVATE_KEY`/`PUBLIC_KEY` affects both apps' logins simultaneously, not just one). Corrected in `internal-tools/shared/context.md`'s Configuration table and `internal-tools/api/context.md` item 29 as part of this session (see `internal-tools/api/decision.md`, 2026-09-17, for the full investigation trail — this correction is cross-cutting infrastructure fact-finding, not an apps/admin-specific decision, so the primary record lives there).

**Copy, not extract, for `GenericServerTable`/`useServerTable`/`RowAction`/`Confirmation` — confirmed, with the real dependency graph traced first.** The brief's instruction was to confirm this is a clean copy. Investigated the actual import graph (not assumed from the four names alone) and found ~13 files total once transitive dependencies (`TableSkeleton`, `TablePaginationComponent`, `tableUtility`, `useMounted`, `useDebounce`, `type.ts`, `OpenDialogOnElementClick`, `FeedbackContext`, `useFeedbackDialog`, `vhyxui-shims/Typography`) are included — all small (largest 65 lines), none carrying apps/web-specific business logic. **Decision: copy the full ~13-file set, not just the four named files** — copying only the four named files and leaving their real dependencies as cross-app imports back into `apps/web/src/...` would violate the brief's own "self-contained" requirement while looking like a smaller, cleaner diff than it actually is.

**Real fit caveat surfaced while tracing the copy, not assumed away:** `GenericServerTable`/`useServerTable` are built for a server that accepts `page`/`limit`/`search`/`sortBy`/`sortOrder`/`filters` (true for apps/web's Members/API Keys/Tunnels). Checked the actual Admin RBAC list endpoints in Part 1's route-reading pass: `GET /admin/users`/`/roles`/`/abilities` accept none of that (at most one hardcoded/simple filter, no pagination params, return everything). **Decision: these three screens use `useServerTable` in client-side-pagination mode** — the same adaptation `internal-tools/user-frontend/context.md` item 47 already documents for apps/web's own Invitations screen when its backend turned out not to support full server pagination either. Not a new pattern to invent, an existing one to reuse. Only `GET /admin/feedback` (found this session, see below) matches the full server-driven shape out of the box.

**New backend surface found and folded into the screen list, not left as a footnote:** `apps/api/src/modules/feedback/presentation/http/feedback.routes.ts`'s `adminFeedbackRoutes` (`/api/v1/admin/feedback`) — list-all-feedback with status/type/priority filters, per-status counts, full page/limit/total pagination, detail view, and a status/priority/notes update endpoint with a documented triage status flow. This was not in the brief's assumed screen list (built from `internal-tools/api/context.md`'s admin-endpoint summary, which only covered the identity module's own routes) and was found only by reading `identity/presentation/http/index.ts`'s route-registration list directly and noticing a second `admin`-prefixed registration alongside the expected one. **Decision: add "Feedback triage" as a 7th initial screen** — it's real, working, already shaped for exactly this kind of admin panel, and skipping it because it wasn't in the original brief would leave a ready-to-use backend surface undiscovered by the next session too.

**Screen list correction — "abilities list (+ create/edit)" from the brief is wrong on one point.** Read `admin.routes.ts` directly: abilities support `GET`/`POST`/`DELETE`, no `PUT`. **Decision: abilities screen is list+create+delete, not list+create+edit** — the plan states this explicitly rather than silently building toward an edit form the backend can't serve.

**Not decided this session, explicitly flagged for the next one:** whether `AdminRole.update()` itself has an `isSystem`-role guard (affects the Roles edit screen's disabled-state UX) — not checked, since it requires reading the entity's method body, judged out of scope for a route-level verification pass. See context.md's Open Questions.

**Status:** active — this is the founding plan for `apps/admin`; the next session should execute Part 3 directly rather than re-investigate.

### 2026-09-17 — Build session: scaffold apps/admin, implement Screen 1 (login) + Screen 2 (dashboard shell), verify end-to-end

**Decided by:** Claude Code (build session, same day as the scoping session above)
**Context:** Executed Part 3 of the scoping session's plan directly, per its own recommendation not to re-investigate. This entry records the judgment calls made during actual implementation — several small, one significant (see the two apps/api bugs, recorded in `internal-tools/api/decision.md` instead, since that's the component the fix belongs to).

**Token storage — decided concretely (the plan left this as "in-memory + a store," not fully specified):** a Zustand store, `persist`-middleware-backed by `sessionStorage`, holding both `accessToken` and `refreshToken`. **Not** `apps/web`'s pattern (memory-only access token, restored via silent refresh against an httpOnly cookie on load) — there's no cookie to restore from. **Not** `localStorage` either, per the plan's own explicit instruction. Chose `sessionStorage` over pure memory-only specifically because `apps/web`'s own `auth.store.ts` already uses `sessionStorage` for its own persisted slice (`user`/`isAuthenticated`) — an already-vetted choice in this codebase for "don't reach for `localStorage`, but some persistence across an in-page reload is still wanted," not a new judgment call invented from scratch.

**`@vhyx/api-kit`'s injection surface — confirmed fitting cleanly, as the plan asked to verify rather than assume.** Read `httpClient.ts` directly: `getAuthHeaders`/`onUnauthorized`/`isPublic` cover exactly what apps/admin's different auth shape needs — a `getAuthHeaders` that reads the store's access token, an `onUnauthorized` that implements the refresh-queue-then-retry pattern with apps/admin's own body-based (not cookie-based) refresh call, and `isPublic: true` on login/refresh themselves. Nothing needed to reach past the package's existing surface. Recorded here since the plan explicitly asked to report back if the fit were awkward — it wasn't.

**Refresh-token rotation, found while implementing (not previously confirmed) — `AdminRefreshToken.usecase.ts` rotates BOTH tokens, with reuse-detection.** The scoping session's Part 1 only checked that `/auth/refresh` exists and returns "a new access token" — reading the use case directly while wiring `http.ts` found it also issues a *new* refresh token every call, revoking the old session and creating a new one, with hard reuse-detection (presenting an already-rotated-away token revokes every session for that admin). Getting this right mattered concretely: `wrapper/http.ts`'s `onUnauthorized` must persist both returned tokens via `setTokens()`, not just the access token — persisting only the access token would have looked correct until the *second* refresh, which would then look like reuse and nuke the session. Verified via a real curl sequence against the live backend (see context.md's Current State) and covered by a dedicated test (`http.test.ts`, "persists BOTH rotated tokens").

**`useFeedbackDialog.ts`'s copy needed a small correction the plan's dependency-graph trace missed.** Part 3.4's table listed this file as self-contained; typechecking the actual copy failed on a trailing `export type {...} from '@/api/domain/feedback/feedback.types'` line — a real import edge the trace's manual reading had missed, pointing at an apps/web-specific module that was never part of the traced ~13-file set. Investigated before just deleting it: grepped `apps/web` itself for any consumer of those three re-exported names via this module's path — none exists (the only real consumer, `FeedbackButton.tsx`, imports the file's own *locally-defined* `FeedbackType`, a same-named but different export). **Decision: delete the line from the copy, don't fabricate a stub `feedback.types.ts` or drag in apps/web's feedback domain module.** It's genuinely dead code in `apps/web`'s own original file too — not flagged as a fix needed there (out of scope), but worth knowing.

**`VhyxUIProvider` needs a real `domain` — found by actually running the dev server, not by reading VhyxUI's source.** The founding plan (Part 3.2 above) chose the full `VhyxUIProvider` over `apps/web`'s narrower `ToastProvider`-only wrapper, reasoning that apps/admin has no legacy reason to withhold it. Running the real dev server surfaced a fatal (though non-blocking-to-render) `VhyxSealError` — `SealProvider`'s manifest generation requires a non-empty `domain`, and neither the `domain` prop nor `NEXT_PUBLIC_VHYX_DOMAIN` were set. **Did not reverse the provider choice** — the concern `apps/web`'s original decision was hedging against ("unverified SealProvider behavior") turned out to be a concrete, fixable missing-required-prop issue, not a deeper problem with the provider itself. Fixed by setting `NEXT_PUBLIC_VHYX_DOMAIN=admin.vhyxvoid.com` in `apps/admin/.env`.

**Server/Client boundary bug on the 5 stub pages — same class of bug `apps/web` already has a documented fix for, re-applied, not rediscovered from scratch.** `internal-tools/user-frontend/decision.md`'s Phase 1 entry ("a genuine Server/Client boundary-crossing file... importing `@vhyxui/react`'s `Button` directly... broke `/profile`'s production build") describes exactly what broke `pnpm build` here too — all 5 stub pages import `Card` directly with no `'use client'`. Fixed the same way that entry's own lesson implies: added `'use client'` to each stub page directly (simpler than `apps/web`'s dedicated-wrapper-component fix, since these are simple leaf pages with no server-side data-fetching reason to stay Server Components).

**Verification method for "prove the whole stack works end-to-end," given no Chrome extension was available:** relied on three converging pieces of evidence instead of one interactive click-through — (1) a real curl sequence against the live backend matching this app's own TypeScript types byte-for-byte (login → `/me` → `/me/abilities` → `/users` → `/roles` → refresh-with-rotation → reuse-detection → logout → post-logout rejection), (2) `http.test.ts`'s 6 tests exercising the identical `getAuthHeaders`/`onUnauthorized` code the real app calls (not a reimplementation — the actual `httpClient` export, fetch mocked), and (3) confirming the real SSR HTML and compiled client bundle are correct (form fields present, correct API base URL inlined). Judged this collectively strong enough to report the auth wiring as verified, while explicitly flagging the one thing it doesn't cover (an actual mouse-click-and-type interactive session) rather than either overclaiming full verification or refusing to report progress for want of a browser tool — matches this project's established practice (`internal-tools/user-frontend/chrome-visual.md`'s entire existence is this same tradeoff, formalized).

**Status:** active — Screens 1-2 real and verified; Screens 3-7 remain stubs for future sessions per the founding plan's Part 3.5 order.

### 2026-09-17 — Screen 3: Admin Users list + detail + role assignment, two real apps/api bugs found and fixed, multi-select question resolved

**Decided by:** Claude Code (third build session, same day as scaffolding+login and the dashboard shell)
**Context:** Executed the founding plan's Screen 3 directly, per the brief's explicit instruction to verify the real backend contract independently rather than assume it matches apps/web's Members screen.

**Real backend contract, verified before writing any UI code, not assumed from the founding plan's own summary.** Re-read `listAdminsSchema` directly: confirmed exactly one real server param (`status`), no page/limit/sort/search — matching the founding plan's claim, but verified fresh per the brief's instruction ("don't assume it matches... verify independently"). Decided to treat `status` as a genuine server-side dimension (a real refetch on change, keyed via `adminUserKeys.list({status})`) rather than folding it into the client-side batch the way Invitations does with its zero real params — a deliberate, new hybrid shape (one real server param + client-side everything else) not previously built in this codebase, reasoned from "use what's real, fake the rest client-side" rather than defaulting to "fetch everything, filter client-side" out of convenience.

**Sort-support verification — done against the real backend before shipping any column as sortable, per the brief's explicit instruction and its own citation of Members' sortBy=name mismatch as precedent.** `GET /admin/identity/users` supports zero server-side sort (confirmed via the schema read above), so every sortable column (name, email, status, last login) is client-side by construction in `paginateAdminUsers` — there was no "does the server actually support this sortBy" question to get wrong here the way Members' did, since nothing is sent to the server for sorting at all. The real risk this session's version of that check guarded against was a mismatch between the *column IDs* (`fullName`, `email`, `status`, `lastLoginAt`) used in `buildColumns` and the `compareAdminUsers` switch's own case labels — verified by direct unit test (`adminUsersTable.util.test.ts`), including an explicit test for the fallback case (an unrecognized `sortBy` silently sorting by email rather than becoming a no-op).

**MultiSelectCombobox — investigated and resolved, not deferred.** The founding plan (Part 1.3/3.5) flagged this as needed "whenever Admin Users or Roles is built." Read `AssignRoleToAdminUseCase`/`RevokeRoleFromAdminUseCase` directly (not assumed from the route file's DTO alone): both take exactly one `roleId` per call, no bulk-assign endpoint exists anywhere in the Admin RBAC backend. **Decision: no multi-select shim, use a plain VhyxUI `Select`** for "add one role," with each already-assigned role shown as an individually-revocable badge — this is not a workaround or a deferred nicety, it's the correct UI for what the real API supports. Flagged (not assumed) that Roles' ability-assignment sub-view almost certainly has the same shape (`assignAbilitySchema` is also singular), since the same investigation should be repeated there rather than taken on faith from this entry.

**Two real apps/api bugs found and fixed — a route-param name mismatch, a different mechanism than the scaffolding session's decorator bug but the same class of "type says one thing, runtime does another."** Building the detail view (`GET /admin/identity/users/:id`) hit a raw `PrismaClientValidationError` immediately on the first real curl call. Traced it: `admin.routes.ts` registers the route as `"/users/:id"` but the handler destructures `const { adminId } = request.params` — Fastify populates `request.params` by the route's actual placeholder name (`id`), never by the handler's own generic type parameter (which claimed `{ Params: { adminId: string } }`, a type assertion with no runtime effect) — so `adminId` was always `undefined`. Checked every other route in the file for the same pattern (a `.get<{Params: {X}}>` mismatch against the route's own `:Y` placeholder) systematically, not just the one hit: a small script cross-referencing each route's path placeholders against its destructured `request.params` keys found exactly one more instance, `POST /users/:id/disable` (identical bug, identical fix), and confirmed every other route (`PUT /users/:id`, `POST /users/:id/enable`, `PUT/GET /roles/:id`, the role/ability assignment routes) is correctly wired. **Decision: fix both, in scope** — same rationale as the scaffolding session's decorator fix (small, safe, purely-corrective change, directly blocking this session's own deliverable, matches this project's established "fix trivial blocking bugs found while verifying" precedent). Verified via real curl against the live backend both before (confirmed broken) and after (confirmed fixed) each change, using a second, non-super-admin test account created specifically so disable/role-assignment testing wouldn't touch the only working login.

**Disjoint-query-key staleness — checked from the start, not assumed away because the app is new.** `apps/admin`'s `GenericServerTable` copy is already the post-Phase-2, props-based version (confirmed by reading the copied file directly, not assumed from memory of what was copied) — the original bug class (an internal `useQuery` keyed separately from what mutations invalidate) cannot structurally recur here. Wrote a real `QueryClient`-based test anyway, per the brief's explicit instruction to verify rather than assume immunity: proves `adminUserKeys.all` invalidation reaches every `adminUserKeys.list({status})` variant via React Query's own partial-key matching, plus a negative case (an unrelated `detail(id)` entry is NOT touched by another admin's invalidation) to confirm the matching is neither too broad nor too narrow.

**"Create Admin" and "Edit profile" forms deliberately not built — a real scope decision, not an oversight.** The brief's Part 2 checklist (query hook, table wiring, sort verification, row actions, mutation-staleness check) and its own framing ("Admin Users list, the first real data screen") didn't ask for full CRUD, and building create/edit forms this session would have doubled the surface area for marginal proof-of-concept value beyond what's already demonstrated by disable/enable + role assignment. The real second test admin needed for safe functional testing was created via a direct `POST /admin/identity/users` curl call instead — matching this project's own established precedent (`LOCAL_DEV_BACKEND.md`'s test accounts were seeded the same way, not through a UI) — and kept as standing test data for future screens (Roles, Abilities will likely also want a non-super-admin target). `useCreateAdmin()` was still built as a real, working mutation hook (wired to the real endpoint, correct invalidation) even though no form calls it yet, so the next session building the create form has nothing left to wire.

**Verification method, same as the scaffolding session, given no Chrome extension was available again (checked first this time, per the brief's explicit "prioritize it if possible"):** real curl sequence against the live backend for every new endpoint (list, detail, disable, enable, assign-role, revoke-role, role-list), a real second test account used throughout (not just asserted safe), SSR/bundle inspection of both new routes, and 15 new tests (10 pure-function, 3 query-key, 2 route-handler regression) — the route-handler regression tests were specifically verified to fail against the pre-fix code before being trusted, matching this project's established discipline.

**Status:** active — Screen 3 (Admin Users: list, detail, role assignment) real and verified; Screens 4-7 remain stubs.

### 2026-09-17 — Screen 4: Admin Roles list + detail/edit + ability assignment + create, isSystem-guard question resolved, ability-assignment asymmetry found

**Decided by:** Claude Code (fourth build session, same day as scaffolding+login, the dashboard shell, and Screen 3)
**Context:** Executed the founding plan's Screen 4 directly, per the brief's explicit instruction to independently re-verify the backend contract (not assume Users' hybrid-pagination/no-multi-select conclusions transfer) and to resolve, not defer, two specific open questions: whether `AdminRole.update()` really rejects system-role edits, and whether Roles' ability-assignment sub-view genuinely needs a multi-select the way Users' role-assignment didn't.

**Pagination shape — independently re-verified, found genuinely different from Users, not assumed to match.** Re-read `admin.dto.ts` directly: no `listRolesSchema` exists at all for `GET /roles` (`isActive: true` is hardcoded server-side, zero query params accepted) — unlike Users, which has one real server param (`status`). **Decision: `paginateAdminRoles` is a new, simpler, fully-client-side function** (search/sort/pagination all client-side over one fetched batch), not an adaptation of Users' hybrid `paginateAdminUsers` (server `status` split + client rest) — closer in shape to the Invitations precedent than to Users' own screen. Verified this was the right call rather than a lazy simplification by actually reading the schema file, not by pattern-matching Users' file structure.

**`AdminRole.update()`'s isSystem guard — resolved concretely, the brief's question #2.** Read `AdminRole.entities.ts` directly: `update()` calls `validateNotSystem()`, which throws `ConflictError('System roles cannot be modified')` for any `isSystem: true` role. Verified empirically via curl against the live backend, not just from reading the source: `PUT` on the seeded "Operator" role → real 409 `CONFLICT`; `PUT` on a custom test role ("Support Agent," created during this session's investigation) → real 200. **Decision: the edit form disables both fields entirely for `isSystem` roles**, with an `Alert` stating the backend enforces this (not just the UI), rather than letting a user submit and hit a confusing 409 — the brief's own stated goal for resolving this question before building the UI.

**Ability-assignment multi-select question — independently re-investigated per the brief's explicit instruction not to assume Users' role-assignment conclusion transfers, the brief's question #1.** Read `AssignAbilityToRoleUseCase`/`RevokeAbilityFromRoleUseCase` directly (not inferred from `assignAbilitySchema`'s shape alone, and not taken on faith from the Screen 3 entry's own speculation that "almost certainly" the same answer applies): both take exactly one `abilityId` per call, upserting/deleting a single `AdminRoleAbility` row. **Decision: same as Users, a plain single-select VhyxUI `Select`** — genuinely re-confirmed, not copy-pasted reasoning.

**New, asymmetric finding this session's investigation surfaced but the brief didn't explicitly ask about — judged worth building the UI around rather than just noting.** Unlike `update()`, neither `AssignAbilityToRoleUseCase` nor `RevokeAbilityFromRoleUseCase` calls `validateNotSystem()` at all — confirmed by reading both use cases (no guard present) and empirically via curl (assigned, then revoked, `audit.read` on the seeded "Operator" system role — both real 204s, no rejection, role's original ability set restored after). **Decision: the ability-assignment sub-view stays enabled for system roles**, with its own `Alert` explicitly distinguishing this from the edit form's block just above it — building it disabled to "be consistent" with the edit form would have been actively wrong, hiding a real capability the backend provides. This is exactly the kind of gap the brief's "verify rather than assume" instruction was guarding against, just surfacing in the opposite direction (a guard NOT present, where the founding plan's speculative framing ("`isSystem` roles are presumably non-editable") could have been read as implying otherwise).

**Create Role form — built this session, a real scope judgment call the brief explicitly asked to make deliberately.** Users' "Create Admin" form was deliberately deferred (password/security complexity, judged out of that session's list+detail+role-assignment scope). `createRoleSchema` is two plain fields (`name` required, `description` optional) — no password, no security-sensitive input, no multi-step flow. **Decision: build it, via a `Dialog` + RHF + yup form matching `apps/web`'s `CreateApiKeyDialog` template** (the established pattern for a small create-dialog in this codebase, not a bespoke design) — proportionate to the actual complexity, unlike Create Admin. Verified via curl before wiring: `POST /roles` → 201, response body `{id, name, description}` — **narrower than `AdminRoleSummary`** (omits `isSystem`/`isActive`). Typed the service call's return value to match the real response exactly rather than the more convenient but inaccurate `AdminRoleSummary`, matching `adminUserService.create()`'s own precedent of a narrow, honest return type.

**No delete/deactivate action built — confirmed absent at the route level, not assumed from the entity's own method surface.** `AdminRole.entities.ts` has `deactivate()`/`activate()`/`canBeDeleted()`, and `deactivateRoleUseCase` is decorated on the fastify instance, but grepping `admin.routes.ts` found no route calls any of them. The founding plan's own screen list (Part 3.5 item 4) only ever said "list, create, edit" for Roles, no delete — this session confirmed that was accurate, not an oversight to fix.

**Abilities sub-resource query key — a hand-built key, not a `.concat()` extension to the shared factory.** A role's assigned abilities don't fit `createQueryKeys`'s `{list, detail}` shape (nested under one role, not a top-level collection). Considered `adminRoleKeys.detail(roleId).concat('abilities')` first (reusing the existing factory's tuple) but found no precedent for that pattern anywhere in the codebase; `apps/web`'s `useOrg.ts` handles the structurally identical case (an org's invitations) with a plain hand-built `['invitations', accountId]` key instead. **Decision: match that existing convention** (`['admin-role-abilities', roleId]`) rather than invent a new one, even though the factory-extension approach would also have worked.

**New `admin-ability.*` scaffold — minimal and read-only, deliberately mirroring how `admin-role.*` itself was first scaffolded (during Screen 3, to support Users' role-assignment dropdown) rather than building out real Screen 5 (Abilities: create/delete) early.** Roles' ability-assignment sub-view needs the full ability list; building only what's needed for that (types, endpoints, service, query keys, one list hook) and leaving create/delete for when Screen 5 is actually built keeps this session's scope to what Screen 4 needs, matching the same discipline Screen 3 applied to `admin-role.*`.

**Type bug fixed in the pre-existing `AdminRoleSummary`, found while extending it, not something this session went looking for.** `description?: string` (added during Screen 3, never itself verified against the real entity) doesn't match `AdminRoleProps.description: string | null` — confirmed by reading `AdminRole.entities.ts`'s own prop types directly. Fixed in place; low-risk (a purely additive type correction, no runtime behavior change, no other file depended on the field being non-nullable).

**Verification method — curl against the live backend for every endpoint the UI calls, per the brief's explicit "no browser check this session, continue with curl/real-backend verification as the standard" direction.** List, detail, create (a disposable "Screen4 Verify Role"), update on both a system role (409 confirmed) and the pre-existing custom "Support Agent" role (200 confirmed), and assign+revoke on both an ability list fetch and a live role (204s confirmed, state restored after) — each checked against the actual TypeScript types before/after wiring, the same discipline as every prior session's functional-verification pass, just without the SSR/bundle-inspection substitute for a browser click-through this time (not needed — the brief deferred that batching decision explicitly, not left as a gap).

**Status:** active — Screen 4 (Roles: list, detail/edit, ability assignment, create) real and verified; Screens 5-7 remain stubs.

**Root cause, found by reading `RowAction.tsx`/`Confirmation.tsx` together, not assumed from the symptom.** `AdminUsersTable.tsx` already computes the exact right guard — `disabled: () => admin.isSuperAdmin || isSelf` — and passes it as `disabled` on the `confirmation`-type row action. But `RowAction.tsx`'s `type === 'confirmation'` branch never read `action.disabled` at all (unlike its `click` and `dialog` branches, which both correctly do `disabled={action.disabled?.(row)}`), and `Confirmation.tsx`'s own `ConfirmationProps` had no `disabled` field to receive it even if it had been forwarded. **This is a real, app-wide gap affecting every `confirmation`-type row action in `apps/admin`, not something specific to the Super Admin case** — any future guard on a confirmation-type action would have silently failed the same way. Checked whether `apps/web`'s own identical copy of these two files has the same gap: it does (confirmed via reading `apps/web/src/libs/components/Confirmation.tsx`/`RowAction.tsx` directly), but grepping `apps/web`'s call sites found none currently set `disabled` on a `confirmation`-type action — so it's a latent, unexercised gap there, not an active bug. **Decision: fix only `apps/admin`'s copy** (the actively-affected one), flag the latent parity gap in `internal-tools/user-frontend/backlog.md` rather than touching `apps/web`'s code, which is out of this fix's scope and risked destabilizing a file with real, working callers.

**Implementation and a real type collision found along the way.** Added `disabled?: boolean` to `ConfirmationProps`, wired it to both trigger-`Button` variants (icon-only and labeled), and added `disabled={action.disabled?.(row)}` to `RowAction.tsx`'s confirmation branch. ### 2026-09-22 — apps/admin production hosting: VPS + Cloudflare Access + same-origin admin API (proposed, awaiting Tanveer's approval)

**Decided by:** Claude Code (investigation; recommendation only, nothing implemented). Supersedes nothing; resolves Phase 0(a) of the 2026-09-22 "Admin Panel v2" entry.
**Context:** Admin Panel v2 needs `apps/admin` reachable in production, but it is not deployed anywhere and its API is already publicly routable. Findings that decide it are in `context.md` ("Hosting and access control for production"): the admin API answers on `api.vhyxvoid.com` today; `admin.`/`ops.` resolve to the origin through the DNS-only wildcard; the VPS has ~123 MB RAM free and cannot build Next; the two sibling `link:` packages block *any* off-repo build (Docker or Vercel); the API's rate limiter likely shares one bucket because `trustProxy` is unset.
**Options considered:** (A) VPS docker-compose + nginx; (B) Vercel; access control: Cloudflare Access, nginx IP allow-list, admin login alone.
**Decision (recommended):** (A) with **Cloudflare Access** in front, **and** serve the admin API through the same host: `admin.vhyxvoid.com` proxies `/` to the admin container and `/api/v1/admin/` to `api:9000`; the `api.vhyxvoid.com` block returns 404 for `/api/v1/admin/`. The build-time `NEXT_PUBLIC_ADMIN_API_URL` becomes a relative `/api/v1`. Admin login stays the second gate. An IP rule may be added inside Access if Tanveer has a static IP. If a memory spike shows the box cannot carry the container, resize the instance; do not move to Vercel for that reason.
**Rationale:**
1. The sensitive surface is the admin API, not the UI hostname. Same-origin proxying puts both behind one Access app, needs no CORS, and removing the path from `api.` closes today's public discovery/brute-force surface.
2. Cloudflare Access is the only option that works from any network, is free at this scale, and pairs with the origin lock already proven on `api.`/`hub.`; an IP allow-list depends on a stable IP nobody has confirmed, and login-only leaves probing open behind a possibly shared rate-limit bucket.
3. Vercel does not remove the real blocker (sibling packages) and adds a second deploy paradigm, a second public entrance (`*.vercel.app`), paid protection tiers, and a cross-origin API; its one real advantage (staying up when the VPS is down) is partial, because the health data comes from the API on that same VPS anyway.
4. The cost of (A) is memory and one off-box build step, both bounded and testable before committing.
**Risks / not verified:** container RAM (~100 MB is an estimate); Next `standalone` output tracing across the linked sibling packages (needs a spike); whether an axios/`@vhyx/api-kit` client accepts a relative `baseUrl`; that the TLS handshake and Cloudflare SSL mode behave as assumed for the new host; Zero Trust sign-up payment requirement; the `trustProxy` consequence was inferred, not tested.
**Next steps if approved (in order):** 1) Tanveer: create the Zero Trust org + Access app + policy (dashboard step, cannot be scripted with the existing DNS-only token). 2) Spikes: memory (`docker run --memory` a built standalone image on the box), `standalone` output with the linked packages, relative `baseUrl`. 3) Decide the sibling-package build path (off-box build with `additional_contexts`/three-repo CI checkout is enough for admin; publishing is the durable fix and also unblocks `apps/web`). 4) `apps/admin/Dockerfile` + `output: 'standalone'`, compose service (`image:`, `mem_limit`, healthcheck, no `ports`), nginx `admin.` block (443, origin lock, wildcard cert, both locations) and add to the port-80 `server_name`, `api.` `location ^~ /api/v1/admin/ { return 404; }`, explicit proxied A record for `admin`. 5) API: set `trustProxy`, add a tighter limit on `/admin/identity/auth/login`, optional `Cf-Access-Jwt-Assertion` validation. 6) Seed production abilities/roles and create the first super admin with a chosen password (script currently hardcodes a default). 7) Deploy, then verify from an unauthenticated browser (Access wall), from the origin IP with a forged Host (403), and `api.` `/api/v1/admin/me` (404).
**Status:** proposed
