### 2026-09-09 — Agent/SDK auth schemes stay permanently separate

**Decided by:** joint (confirmed independently by two prior build sessions)
**Context:** Agent registration uses raw-secret HMAC; SDK/API requests use full canonical-signature verification with replay protection. Audit flagged this as a possible unintentional duplication.
**Options considered:** unify onto one scheme; keep both.
**Decision:** Keep both, permanently.
**Rationale:** Agent registration is a one-time trusted-process handshake over a persistent connection — no replay risk. SDK/API calls are per-request over untrusted networks and need timestamp/replay protection. Unifying would require agents to know the HMAC pepper, which was deliberately kept off the agent.
**Status:** active

### 2026-09-12 — nginx/TLS cert: the SAN theory was wrong, but the live cert is actually expired

**Decided by:** Claude Code (Hub audit session)
**Context:** context.md risk #2 theorized `hub.vhyxvoid.com`'s nginx block pointing at the `api.vhyxvoid.com` certbot lineage path might mean `hub.vhyxvoid.com` isn't covered by the served cert's SAN list — flagged as needing a live check, assumed no server access would exist. This session found the sandbox **does** have live network egress and ran the check directly: `openssl s_client -connect hub.vhyxvoid.com:443 -servername hub.vhyxvoid.com` (also repeated against `api.vhyxvoid.com`).
**What the live check actually found:** the SAN theory was wrong to worry about — the served certificate's SAN is `DNS:*.vhyxvoid.com, DNS:vhyxvoid.com` (a wildcard), so `hub.vhyxvoid.com` is covered regardless of which lineage directory name certbot filed it under. TLS handshake and chain validation succeed. **However, the certificate itself is expired**: `Not After: Aug 3 21:03:51 2026 GMT`, checked against the live system clock `Sat Sep 12 08:32:46 UTC 2026` — over 5 weeks past expiry, on both `hub.` and `api.` subdomains (same cert). `curl -k` (skipping verification) gets a 200 from both `/health` endpoints, meaning the services themselves are up; only the TLS handshake's certificate-validity check fails, which most real clients (browsers, most HTTP client libraries without a verification override) would refuse to complete.
**This is a live, active production issue, not a repo-fixable one.** Certbot's renewal automation (the `certbot` service in `docker-compose.yml`, per context.md's Tech Stack section) has evidently not run successfully in over a month. Nothing in this repo can fix a live server's certificate — this requires direct server access (SSH to check `certbot renew`/its cron or systemd timer/its container logs) that this session does not have.
**Decision:** Do not attempt a repo-side workaround. Documented precisely (dates, exact commands run, exact findings) in context.md so the user can act on it directly. This is the one item from today's audit that requires the user to run something on the actual live server themselves.
**Severity note:** ranked this above the original SAN question in urgency — an expired production cert affecting all HTTPS traffic to both `api.` and `hub.` subdomains for 5+ weeks is a bigger, more immediate problem than the theoretical SAN mismatch this item originally set out to check.
**Status:** confirmed via live check — SAN question resolved (fine), cert-expiry finding requires user action outside this session's reach

### 2026-09-12 — bodyEncoding: fixed a real data-corruption bug, scoped to the response path only

**Decided by:** Claude Code (Hub audit session)
**Context:** context.md risk #21 described `tunnel:forward`'s missing `bodyEncoding` field as making binary detection "fragile" (inferred from Content-Type). Investigating `packages/agent/src/proxy/BackendProxy.ts` directly found this understated the actual bug: `forward()` unconditionally did `bodyBuffer.toString("utf8")` on every backend response regardless of content type — a **lossy, irreversible** decode for any binary response (images, PDFs, etc.). By the time the hub's `HttpTunnelHandler.writeResponse()` tried to `Buffer.from(response.body, 'base64')` based on content-type sniffing, the bytes were already corrupted; sniffing was never the actual bug, silent data corruption upstream of it was.
**Scope decision:** Fixed the response path (Backend → Agent → Hub → real HTTP client), which is the one path fully contained within this session's Hub-audit boundary and the one confirmed corrupted:
- `packages/protocol`: added optional `bodyEncoding?: 'utf8' | 'base64'` to `TunnelResponseMsg` and `SdkResponseMsg` (backward compatible — an older agent that never sets it falls back to the receiver's existing content-type sniffing).
- `packages/agent`'s `BackendProxy.forward()`: now detects binary content type and base64-encodes instead of always UTF-8-decoding; `ResponseCache`'s `CachedResponse` also carries `bodyEncoding` so a cache HIT doesn't lose it.
- `apps/hub`'s `HttpTunnelHandler.writeResponse()`: prefers the explicit `bodyEncoding` field when present, falls back to content-type sniffing when absent.
- `apps/hub`'s `Message.router.ts`: passes `bodyEncoding` through into `SdkResponseMsg` for the WS/`sdk:request` path.
**Explicitly NOT fixed this session, flagged as follow-up:** (1) the SDK client (`packages/sdk`'s `TunnelClient`/`client.ts`) does not yet decode a base64 `bodyEncoding` on the `sdk:response` path — the field is now propagated correctly but nothing consumes it yet, so binary responses via the WS/SDK path (as opposed to the raw HTTP tunnel path via `accountslug--label.vhyxvoid.com`) are still corrupted until the SDK is updated too. (2) The *request* direction has the mirrored bug — `HttpTunnelHandler.readBody()` also does `Buffer.concat(chunks).toString('utf8')` unconditionally, meaning a binary file uploaded through a tunneled subdomain would be corrupted before it ever reaches `TunnelForwardMsg.body`. Fixing this symmetrically requires auditing the SDK's own request-body encoding assumptions too (does it already base64 anything before sending? unverified) — genuinely wider ripple than the response-path fix, per the brief's explicit "flag rather than implement if it turns out to have wider ripple effects." Both are real, confirmed-present gaps, not speculative.
**Tested:** `tests/e2e/backendProxyBodyEncoding.test.ts` — binary (PNG) response round-trips byte-for-byte through base64, JSON response stays plain utf8, empty body stays null regardless of content-type. Uses a real local HTTP server on an ephemeral port as the backend rather than mocking axios (see the test-infra entry below for why).
**Status:** active — response path (raw HTTP tunnel) fixed and tested; SDK/WS path and request-direction corruption are new, confirmed, unfixed follow-up items

### 2026-09-12 — better-sqlite3's native binding was silently never built (pnpm-workspace.yaml misconfiguration), discovered while making queueReplay.test.ts real

**Decided by:** Claude Code (broken-test-repair session)
**Context:** Writing a real `queueReplay.test.ts` against `DurableQueue` (real SQLite via `better-sqlite3`) failed immediately with "Could not locate the bindings file" — `better-sqlite3`'s native addon had never been compiled/downloaded in this environment. Investigating why (rather than just working around it locally) found the root cause is a **committed, project-wide config**, not a sandbox quirk: `pnpm-workspace.yaml` listed `better-sqlite3` under `ignoredBuiltDependencies`, and pnpm 10's build-approval security feature means any package's `install`/`postinstall` script is skipped unless explicitly allow-listed via `onlyBuiltDependencies` (which only listed `prisma`). `better-sqlite3`'s own `install` script is exactly what runs `prebuild-install` (download a prebuilt binary) or falls back to `node-gyp rebuild` — with that script silently skipped, the binding never gets created on any fresh `pnpm install`, in this sandbox or anywhere else, CI included.
**Real-world consequence, not just a test-infra inconvenience:** `DurableQueue` is genuine production code — `AgentClient`'s default (non-`disableQueue`) path, used by every CLI-mode Agent deployment. **Any fresh clone + `pnpm install` of this repo would leave a real Agent CLI unable to start** the moment it needs to write to its durable queue (WS disconnect → outbound queue write), throwing the exact "Could not locate the bindings file" error this test hit — previously undiscovered because no session had exercised `DurableQueue` directly (Hub audit's `packages/middleware` work specifically avoided it via `NoOpQueue`/`disableQueue: true`, and nobody had run the CLI path fresh in a while). Confirmed via `esbuild` comparison: `esbuild` is also in `ignoredBuiltDependencies` but is harmless there, because its actual platform binary ships as a separate `@esbuild/<platform>` optional dependency resolved by npm/pnpm directly, not via a custom install script — `better-sqlite3` has no such fallback.
**Options considered:** (1) leave `pnpm-workspace.yaml` alone, and just manually build the binding in this sandbox so the new test passes here (a local-only fix that leaves the real bug — and the test's portability to CI/other machines — broken); (2) move `better-sqlite3` from `ignoredBuiltDependencies` to `onlyBuiltDependencies` so `pnpm install` builds it automatically and non-interactively everywhere, including CI.
**Decision:** Option 2. `pnpm-workspace.yaml` now has `onlyBuiltDependencies: [prisma, better-sqlite3]` and `better-sqlite3` removed from `ignoredBuiltDependencies`. Verified by deleting the already-built binding directory and the package's own install output entirely, then running `pnpm install`/`pnpm install --force` fresh — confirms the binding is rebuilt automatically without any manual `prebuild-install`/`node-gyp` intervention this time (see session_update.md for exact verification steps and timing).
**Rationale:** This is exactly the kind of silent, easy-to-miss regression the project has asked to catch mechanically (per this session's own CI ask) rather than rediscovering per-session — fixing it here, while already in the file for test-writing reasons, is the correct scope (a one-line config correction to a real, confirmed production gap), not scope creep. Leaving it broken would also have made the new `queueReplay.test.ts` non-portable — passing only in a sandbox with a manually-built binding, failing again for the next session or in CI.
**Status:** resolved — verified via a from-scratch reinstall, not just re-running the already-fixed local state

### 2026-09-13 — Request-direction body corruption: symmetric fix, WS SDK path confirmed out of scope (can't carry binary today)

**Decided by:** Claude Code (bodyEncoding follow-up session)
**Context:** context.md risk #21 / decision.md's 2026-09-12 "bodyEncoding" entry also left `HttpTunnelHandler.readBody()`'s mirrored request-direction bug unfixed, explicitly because "fixing this symmetrically requires auditing the SDK's own request-body encoding assumptions too (does it already base64 anything before sending? unverified)." **Investigation:** `TunnelClient.request()` does `bodyStr = params.body != null ? JSON.stringify(params.body) : null` unconditionally — the WS SDK path can only ever send JSON-serializable values, never raw binary, and never has, so there is no existing SDK-side base64 encoding to mirror and no way for a caller to trigger this bug through `TunnelClient` today. The actual corrupted path is the raw HTTP tunnel path — any HTTP client (curl, a webhook provider, `client.ts`, or literally a browser `<form>`) POSTing a binary body directly to `accountslug--label.vhyxvoid.com`, which `HttpTunnelHandler.readBody()` receives and unconditionally `.toString('utf8')`'d.

**Tested:** `tests/e2e/tunnelRequestBodyEncoding.test.ts` — `HttpTunnelHandler.handle()`'s encode side (against fake registries + a real HTTP request, binary/JSON/bodyless-GET cases), `BackendProxy.forward()`'s decode side (binary/utf8/missing-bodyEncoding-treated-as-utf8 cases) against a real local backend server, and a full in-process round trip (hub encode → agent decode → real backend receives the exact original PNG bytes) — the literal scenario the brief asked to verify.

### 2026-09-19 — SDK reclassified as Node-only (not browser-capable); TunnelClient reframed as a Node persistent-connection option

### 2026-09-20 — WS-through-tunnel: reframed from "build Phase 2" to "harden the existing relay"; auth posture, limits and Origin handling deliberately left undecided

**Decided by:** Claude Code (investigation session; design only, no implementation)
**Context:** The brief asked for a design to add WebSocket support for tunnel subdomains, on the premise that `HubServer.ts` only accepts upgrades on `/agent` and `/sdk` and a tunnel-subdomain upgrade 502s.
**What was found:** The premise is false. `HubServer.ts:309-315` already routes tunnel-host upgrades to `HttpTunnelHandler.handleWebSocket`; the agent side (`AgentClient.onWs*`, `BackendProxy.openWebSocket`) and the protocol messages exist (commit `6cac7b7`); nginx's wildcard block already forwards Upgrade/Connection through `$connection_upgrade`; a live upgrade to an unregistered tunnel host returned the hub's own `404` (a pre-`6cac7b7` hub would return `400`), so production runs the handler. The "Phase 2" comment at `HubServer.ts:317-320` is stale. A 502 could not be reproduced (the hub emits it only when `handleWebSocket` rejects; nginx emits it when the hub is down).
**Options considered:** (a) write the greenfield design the brief described; (b) report the premise is wrong and stop; (c) report it, empirically test the existing relay, and design the hardening + missing lifecycle.
**Decision:** (c). A greenfield design would have duplicated code that already exists and hidden that it is broken. Built a scratch harness (real hub `HttpTunnelHandler` + `MessageRouter`, real agent `BackendProxy` + `MessageBatcher`, real `ws` backend; kept in the session scratchpad, not the repo) and confirmed ten defects (D1-D10 in `internal-tools/shared/ws-tunnel-design.md`), the most serious being silent loss of WS frames whenever 2+ arrive within the 50 ms batch window (hub `handleAgentBatch` has no WS case), broken subprotocols (Vite HMR), and leaked connections on agent disconnect. Refuted one hypothesis (duplicate handshake headers) so it is not chased again. Design chose: a separate `TunnelWsRegistry` (not `PendingRegistry`, whose request/response+timeout contract doesn't fit), deferred 101 until the backend accepts (removes early-frame buffering entirely), WS frames bypass the batcher and never enter the durable queue, additive protocol only with capability-gated legacy mode, no session resumption across agent reconnects (consistent with the accepted inbound-replay gap), no Redis mirror (nothing recoverable; keeps single-hub constraint).
**Explicitly NOT decided (the brief asked for the trade-off, so it was presented, not settled):** auth posture for tunnel WS (recommendation recorded: parity with HTTP + caps, tunnel access tokens as a separate HTTP+WS project), all limit numbers (placeholders), idle policy, Origin rewrite, usage accounting, frame encoding, agent-drop close code. See the design doc §5.

### 2026-09-20 — WS relay Phase 1: judgment calls (agent-side changes despite "hub-side only", registry access, replaced-session cleanup, info-leak scope) and a correction to the DNS finding

**Decided by:** Claude Code (Phase 1 implementation session)
**Context:** Phase 1 of `ws-tunnel-design.md`, briefed as "hub-side only, no protocol changes".
**Decisions:**
1. **Agent-side edits were made despite "hub-side only".** D2 (close overtaking buffered frames) and D5's agent half (`AgentClient.onClose` never closing backend sockets) cannot be fixed on the hub: the ordering inversion is created inside the agent's batcher. The brief's own items 4 and 5 name them, so the agent change was treated as in scope; "no protocol changes" was read as "no wire-format changes" (satisfied: only a type union was widened and a pure helper `toSendableCloseCode` added). 2. **The router reaches the registry through `HttpTunnelHandler`, not by holding it.** The design suggested injecting `TunnelWsRegistry` into both. `MessageRouter` already holds the handler and has 13 constructor args; `closeAllForAgent`/ownership checks are one-line delegations. The handler owns the registry (constructor-injectable, defaults to a fresh one so HTTP-only test constructions are unchanged).
3. **Ownership is resolved from the socket, not the message.** The router derives the sending agent from `agentRegistry.findByWs(ws)`; an unregistered socket's tunnel:ws:* frames are ignored. A message field would be attacker-controlled.
4. **Same-label re-registration is cleaned up in `handleAgentRegister`.** Found while wiring D5: `AgentRegistry.register` evicts the old session and closes its socket, whose close event then finds no session, so `onAgentClose` never runs for it and its tunnels would be orphaned. 7. **`teardown` is the single idempotent close path;** a browser `close` handler that finds its entry already removed does nothing, so agent-initiated/dropped-agent closes never bounce a second `tunnel:ws:close` back.
8. **Tests drive the real `AgentClient`** (private `ws`/`state` set in-process) instead of mirroring its wiring as the scratch harness did — a mirrored copy would have passed regardless of the D2/D5 agent fixes.

### 2026-09-22 — Fixed the SUSPENDED-reactivation gap (hard prerequisite for S4/admin-suspend): guarded PAST_DUE-to-ACTIVE, both call sites, same discipline as markPastDue

**Decided by:** Claude Code (implementing the hard-prerequisite fix flagged in "Answers to the E1-E7 open questions"; commits `069f3d9` code, `bfe660b` docs; not deployed)

1. **Part 2 — public-path limiting mechanism, proposed.**

**2.1 — Two separate mechanisms, not one, because they have different jobs and different failure tolerances:**
- **(a) A real-time, in-process, per-account, per-minute abuse limiter** — a `Map<accountId, {minuteBucket, count}>` inside the hub process (same minute-bucket format as `validateApiKey.ts`'s existing `currentMinuteBucket()`, reused for consistency), checked synchronously in `HttpTunnelHandler.handle()` before forwarding. **No Redis command per request** — this is the brief's own framing and the right call given today's single-hub deployment (`HubPubSub`/multi-hub is a confirmed stub, Known Risks #9) and given public-path volume (unsigned webhook/browser traffic, potentially much higher than the already-expensive-to-produce signed SDK requests) is exactly the traffic Upstash's per-command billing would punish hardest. This governs the 429 in Part 2.3.
- **(b) A batched, Redis-backed, per-account monthly counter** for the (already-decided-soft, decision.md "Answers to the E1-E7 open questions" #6) `maxRequestsPerMonth` display/warning. Accumulate in-process per account, flush on a ~30s interval (same shape as `AccountStatusSweepService`'s own interval, `apps/hub/src/services`) as one `INCRBY` per account with a nonzero delta into `usage:{accountId}:{PUBLIC_USAGE_SENTINEL}:requests:{bucket}` — reusing `HubUsageService.increment()` (freed up by the Part 3 fix below) rather than a new Redis wrapper. `PUBLIC_USAGE_SENTINEL` (proposed literal: `"_public"`, exported from `packages/shared` so both the hub writer and the api reader use the same constant, matching how `CONNECTABLE_ACCOUNT_STATUSES`/`PLAN_LIMITS` were centralized in S3/S4) needs one small, contained change on the read side: `RedisApiKeyCacheService.drainUsageCounters()` (`apps/api`, `:224-244`) currently always sets `apiKeyId = parts[2]` verbatim; it should map the sentinel to `null` before calling `upsertQuantity`, landing it in `UsageAggregate` as the account-level rollup row the schema already has a documented slot for. This is the only DB-shaped change either mechanism needs — no new table, no new migration.
- Batching (b) instead of one Redis command per request (matching (a)'s reasoning) trades a small amount of freshness (up to ~30s of counts lost on a hub crash) for a large reduction in Redis command volume on high-traffic public tunnels; acceptable because this counter is explicitly soft/informational (decision.md #6), not a billed or hard-enforced number.
- Plan lookup: neither mechanism should hit Postgres per request. Cache each account's resolved `PlanLimits` in-process with a short TTL (propose 60s, matching the sweep's own cadence), lazily refreshed via the same `TunnelSessionRepository.findPlanLimitsForAccount` S3 already added for the agent-limit check. **Failure fallback, deliberately matching S3's own precedent for the identical failure mode (E1, "Answers to the E1-E7..." decision.md entry, Part 2 item 4): if the plan lookup fails, apply the PRO number, logged** — not unlimited (would silently defeat the limiter on a DB blip) and not refuse-everything (nothing about the specific request caused the failure).

**2.2 — Concrete numbers, proposed (not decided):**
- Per-minute public-path abuse limiter (new, per account, all labels combined): **FREE 300/min, PRO 3,000/min, ENTERPRISE unlimited.** Reasoning: FREE's existing per-*key* SDK limit is 60/min (`PLAN_LIMITS.FREE.rateLimitPerMinute`) but that gates one signed, deliberately-called SDK request at a time; the public path aggregates all unsigned traffic to an account's tunnel URL(s) at once (webhook retries, a browser hammering a page, a misconfigured client) and FREE only ever has 1 agent (S3) so a 5x multiplier over the per-key number still comfortably allows a developer's own rapid manual/test-suite traffic (5 req/s sustained) while catching a genuine flood. PRO gets a 3x multiplier over its own per-key number (1,000/min) rather than a flat multiple of FREE's, since PRO accounts run up to 5 agents (S3) whose combined webhook traffic should be allowed to run meaningfully hotter than one FREE agent's. ENTERPRISE unlimited matches every other ENTERPRISE row in `PLAN_LIMITS` (agents, members, monthly requests, per-key rate) — no reason to be the first exception.
- `maxRequestsPerMonth` itself: **recommend leaving the existing values (FREE 1,000 / PRO 50,000 / ENTERPRISE unlimited) unchanged for now**, per the already-decided soft/count-only semantics — but flagging, not deciding: FREE's 1,000/month was set before either path counted anything real; once public-path traffic is counted for the first time, an account doing ordinary webhook-testing dev work will likely blow past 1,000 within days, which makes the planned "warn near/over the limit" UI (decision.md #6) fire almost immediately for nearly every real FREE user — a "1000%+ over your limit" warning that fires for normal use stops meaning anything. Worth Tanveer revisiting the FREE number specifically once real counted data exists (a few weeks after S5 ships), not blocking S5 on it now.
- 429 body/headers, matching the existing `HttpTunnelHandler.sendError()`'s shape (`{error, status, tunnel: true}`, `apps/hub/src/handlers/HttpTunnel.handler.ts`) rather than inventing a new envelope, plus one addition neither `sendError` nor any other hub HTTP response currently sets: a `Retry-After` header (seconds to the next minute boundary) and a matching `retryAfterSeconds` body field — well-behaved webhook senders (Stripe, GitHub, etc.) honor `Retry-After`, and nothing in this codebase sets it today.
- Fail-open/closed: the real-time in-process limiter can't meaningfully "fail" independent of the hub itself being down (no external dependency) other than the plan-lookup-cache-refresh case already covered above (falls back to PRO's number, logged). The batched Redis flush (mechanism (b)) fails open, silently dropping that interval's delta on a Redis error and retrying next interval — matching the universal precedent already in this codebase for usage/rate-limit accounting (`HubUsageService.increment().catch(() => {})`, `validateApiKey.ts`'s `incrementRateLimit` "fail open on Redis error", `incrementUsage`'s fire-and-forget `.catch(() => {})`) — usage accounting must never affect whether a tunnel request succeeds.

""` while its own `create()` branch wrote a real `null`: those can never match each other, and — confirmed by `tsc`, not assumed — Prisma 6's compound-unique `where` shorthand rejects a literal `null` outright (a known Prisma limitation for composite indexes with a nullable member, not something this project's schema did wrong). 1. **Preflights go to the backend, not a hub-built "safe" answer.** Options: keep answering `OPTIONS` at the hub but without credentials or reflection; forward it. Any hub-built answer is a policy the backend didn't choose (and a non-credentialed wildcard still breaks backends that use cookies). Building an opt-in now would recreate C3 for whoever enables it; per-account sharing belongs to A1 (cookies scoped to `.<slug>.<tunnel-domain>`).
5. **Hub-generated error responses (404/429/502/503/504) still carry no CORS headers**, unchanged; the old code never added them there either.
6. **The product premise is reversed for now, on purpose.** `context.md`'s Product Vision ("cookie-domain sharing … auth/cookies/CORS just work") was exactly the cross-tenant exposure. It returns, scoped per account, with A1.

### 2026-09-24 — H5/H6: compressed-response length fixed on both hub and agent; nginx tunnel body cap to 10m

**Decided by:** Claude Code (commits `58a98f1` H5, `86397d5` H6, docs `2a7870c`; not deployed)
**H5 context:** audit H5. The mismatch is introduced in the **agent**: axios `decompress: true` inflates gzip/br/deflate and deletes `content-encoding` but keeps the backend's compressed `content-length`; `sanitizeOutboundHeaders` forwarded it and the hub's `writeResponse` set it on the real response, so callers read only the compressed byte count. Reproduced first by a new end-to-end test (real compressing backend → real `BackendProxy` → real `HttpTunnelHandler` → real HTTP client): 6/7 cases fail on the old code (e.g. agent reports 204 for a 1861-byte body).
**Options considered:** agent only (fixes nothing until every developer upgrades); hub only (works for all installed agents on deploy, but the agent's headers and its response cache stay wrong); `decompress: false` passthrough (cheaper, audit P1, but changes what backends' consumers see and interacts with the agent cache and bodyEncoding sniffing; a larger change); both sides recompute.
**Decision:** both. Hub: builds the payload first, ignores the agent's `content-length` whenever there's a body, and sets `Content-Length` from the bytes written. Agent: after sanitizing, sets `content-length` to the decoded body's length. Body-less responses (HEAD, 204, 304) keep the backend's value on both sides: it describes a body that isn't sent, and dropping it would change HEAD semantics. `content-encoding` needs no handling: axios removes it exactly when it decompressed, and an encoding axios doesn't decode (e.g. zstd) passes through with its bytes still encoded and its original length, which is then correct. `decompress: false` stays a separate performance item (audit P1). No agent publish is needed for the fix to take effect; the agent half ships with the next agent release.
**H6 decision:** `client_max_body_size 10m;` in the wildcard tunnel server block only: equal to the hub's `MAX_BODY_BYTES` and the protocol's `MAX_PAYLOAD_BYTES` (both `10 * 1024 * 1024`, nginx `m` = 1024²). The api block keeps nginx's 1 MB default, which equals Fastify's own default `bodyLimit` (no api route takes uploads), so raising it would only move the 413 into Fastify. The `hub.vhyxvoid.com` block carries WebSockets, whose frames this directive doesn't govern. Validated with `nginx -t` (and `nginx -T` showing the directive) in a throwaway `nginx:alpine` container on the server with the server's certs and Cloudflare includes mounted read-only; the running nginx was untouched.
**Deploy note (H6 differs from api/hub):** nginx isn't an image from the GHCR workflow; it bind-mounts `~/Vhyxvoid/nginx.conf` as a single file. `git pull` replaces the file with a new inode, and a single-file bind mount keeps pointing at the old one, so `nginx -s reload` may keep serving the old config. After pulling: `docker compose up -d --force-recreate nginx` (a second or two of downtime for api, hub and tunnels), then `docker compose exec nginx nginx -T | grep client_max_body_size`. Recorded in `shared/backlog.md`.
**Docs:** `check:fresh` flagged 11 pages citing the two touched source files; all re-read, none described compression or response length, and every body-limit statement already said 10 MB with the hub's 413 (true behind nginx only after H6). `verified.commit` bumped, nothing else.
**Status:** active.

### 2026-09-24 — H8/H9: replay window and canonical format; origin-form paths enforced at hub and agent

### 2026-09-25 — Audit part2 G1/G3/G4/G7: in-memory hold instead of plain removal, 1 MB batches, middleware opt-in with a CI check

**Decided by:** Claude Code (commits `4319aa6` G1, `2f90df4` G3, `6ad687e` G4, `bd02394` G7, docs `ff0d2ea`; not published). Source: `audit-2026-09-24-part2.md`.
**G3, the brief's premise corrected twice before changing anything:**
1. *"Inbound replay is a separate, working mechanism."* It isn't: nothing calls `enqueueInbound`, so inbound replay has no producer. Only outbound persistence was in scope, so inbound was left exactly as it was; the no-producer finding went to `backlog.md` (delete the queue and `better-sqlite3`, or build inbound replay properly).
2. *"Queued outbound responses are essentially never delivered."* Almost, not quite: after a half-open drop (agent sees the close, hub doesn't yet), a same-label reconnect makes `AgentRegistry.register` evict the old session, whose close then finds no session, so its pending requests are not rejected, and `handleTunnelResponse` accepts a response from the new socket. A response sent within the 120 s pending window is delivered.
**Options:** (a) delete outbound replay outright (what the brief named); (b) keep it on disk encrypted; (c) hold in memory only. **Chose (c)**, which is the report's own alternative: it keeps the one real benefit, puts nothing on disk, and removes the key-management question (b) would raise. Bounds: 100 responses, 20 MB, and `TIMING.REQUEST_TIMEOUT_MS` (older ones can't match a pending entry). In-process agents (next/middleware) get the same hold; they used to drop these responses. Legacy outbound rows are purged when the queue opens, so upgrading also removes old bodies from disk. `enqueueOutbound` removed from `DurableQueue`/`NoOpQueue` rather than kept as a deprecated no-op, so the unsafe behaviour can't come back through the exported class; this is a public-API removal (agent minor bump). If the hub ever adds an ownership check on `tunnel:response` (first audit M2), it must accept a response from a new session of the same account and label, or this path stops working.
**G4:** 1 MB, the report's number, far under the hub's 100 MiB `maxPayload`. A message over 1 MB goes alone after the buffer is flushed (order kept). Each message is serialized once in `add()` and batches are concatenated from those strings (byte-identical to `serialize()`), so a 10 MB body isn't stringified twice. The disconnected path still hands message objects to the fallback.
**G7:** the rule is `@vhyxvoid/next`'s (`NODE_ENV === 'development'`) plus a CI check (`CI` set and not `false`/`0`); explicit `enabled` wins either way. Breaking for anyone relying on the old default, called out in the commit, the source comment and the docs; the version bump is left to the publish session. next itself was not changed (out of scope; backlog).
**G1:** aliasing in SQL, as the brief suggested, with one shared column list so a future query can't reintroduce the mismatch.
