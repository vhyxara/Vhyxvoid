- [ ] **`packages/sdk` `TunnelClient` cannot authenticate (`/sdk` WS path).** `TunnelClient.ts` signs `sdk:register`/`sdk:request` with `signCanonical(canonical, config.secret)`, and `types.ts` documents `secret` as the "raw secret returned at key creation". The hub verifies through `packages/shared/src/validateApiKey.ts`'s `verify(cached.secretHash)`, i.e. keyed by `HMAC-SHA256(pepper, rawSecret)`, which a client can't compute without the server pepper (deliberately kept off clients, shared/decision.md 2026-09-09). So every real `TunnelClient` user gets INVALID_SIGNATURE. It also blocks runtime proof of the `62ddc08` sdk:request dedup fix. Not a one-line fix: it needs a decision on whether the verifier accepts a raw-secret-keyed HMAC (the server holds only the hash), whether key creation hands out a derived signing secret, or something else. `packages/protocol/src/canonical.ts`'s "Agent signs using the same secretHash" comment is also misleading (agents send rawSecret, not a signature). Found 2026-09-24 via the S5 close-out report, confirmed by code reading. **Update 2026-09-24 (usage-drain fix session):** confirmed live against a local hub: a harness sending `TunnelClient`'s exact `sdk:register`/`sdk:request` messages but signed with `HMAC-SHA256(pepper, rawSecret)` registers and gets 200s, so the hub side is fine and the fix is purely client/credential design. **Update 2026-09-24 (audit H8, `222546f`):** the canonical string changed (length-prefixed `vv2`, query signed, 30 s skew), and `TunnelClient` already signs through protocol's `buildCanonical`, so the bug #1 fix picks the new format up automatically; the published sdk 1.1.0 bundles the old protocol and would fail on format even with the right key. The same run confirmed the `62ddc08` dedup live: 2 requests left the counter at 3 (1 per request, plus the handshake, see next item), where the pre-fix code would have left 5.
