## 1. New gaps and hidden bugs (not in `claude-output.md`)

### G1. The agent's dead-letter queue never triggers, so failed items retry forever (High, correctness)
`packages/agent/src/queue/DurableQueue.ts`
- The SQL selects snake_case columns (`max_attempts`, `next_retry_at`, lines 123 and 142), but the TS type and `markFailed` read camelCase: `if (newAttempts >= item.maxAttempts)` at line 146.
- `item.maxAttempts` is `undefined`, so the comparison is always `false`, and an item is **never** moved to `dead_letter`. It retries every ≤300 s forever.
- For inbound items, each retry re-executes the request (possibly a POST) against the local backend.
- `drainForReplay()` also returns objects whose `nextRetryAt`/`maxAttempts` are undefined, so `replayQueue`'s logging and any consumer of those fields is wrong.
- Fix: alias the columns in SQL (`max_attempts AS maxAttempts, next_retry_at AS nextRetryAt`) and add a test that fails an item N times.

### G2. The durable queue is shared by every agent on the machine (Medium)
- The default path is `~/.vhyxvoid/queue.db` regardless of label or port (`AgentClient` constructor).
- Two CLI agents on one machine (e.g. `api` on :4000 and `web` on :3000, the documented multi-label setup) share one queue.
- Agent B's `replayQueue` drains agent A's items: outbound responses are sent over B's hub connection, and inbound requests are replayed against **B's port**. The first-pass M2 (no ownership check on `tunnel:response`) means the hub may even accept them.
- Fix: default to `~/.vhyxvoid/queue-<label>-<port>.db`, or add a `label` column and filter on it.

### G3. The outbound replay queue can essentially never deliver anything useful (Medium, wasted work and data at rest)
- The hub drops any `tunnel:response` whose pending entry is gone (`Message.router.ts` "unknown/timed-out request").
- Pending entries live ≤120 s (`TUNNEL_REQUEST_TIMEOUT_MS`), and on a **new** hub connection all of the previous connection's pending entries have already been rejected (`rejectAllForAgent` on close). A response queued during a disconnect is therefore never matched after reconnect.
- Meanwhile full response bodies, which may include auth tokens or PII from the developer's backend, are written unencrypted to SQLite in the home directory. They stay there until the next successful connect, or forever for a CLI user who never reconnects.
- Recommendation: drop outbound persistence entirely, or keep it only in memory for the ~10 s reconnect window and only if the hub keeps pending entries across a same-label reconnect (see A3).

### G4. Batches have no byte limit, so a burst of large responses disconnects the agent (High, stress)
`MessageBatcher` flushes on count (100) or time (50 ms), never on **size**.
- Eleven concurrent 10 MB responses (base64 → ~13.3 MB each) inside 50 ms produce one ~146 MB `agent:batch` frame.
- The hub's `maxPayload` is 100 MiB (`HubServer.ts:318`), so `ws` closes the agent with **1009 Message Too Big**. Every in-flight request is rejected and the agent reconnects.
- At larger volumes `serialize()` can exceed V8's max string length and throw `RangeError: Invalid string length` inside a `setTimeout`, which is an uncaught exception that kills the CLI agent.
- Fix: flush when the buffered bytes exceed ~1 MB, and send any single response larger than ~1 MB un-batched. Longer term, stream bodies (see A2).

### G5. ResponseCache has an entry cap but no memory cap (Medium)
- `MAX_ENTRIES = 500` but no byte budget: 500 × 10 MB bodies is ~5 GB (or ~6.7 GB as base64 strings) inside the developer's own process. With `@vhyxvoid/next`/`middleware` that is the **user's app process**.
- Eviction is FIFO, not LRU, so hot entries are evicted before cold ones.
- A browser hard-refresh (`Cache-Control: no-cache` / `Pragma: no-cache` on the **request**) is ignored and still gets a HIT.
- `invalidatePrefix` matches by string prefix, so a POST to `/api/users/5` invalidates `/api`, `/api-docs`, `/apiary`… (over-invalidation, harmless). But a POST to `/users` (base path `""`, falling back to `/users`) does **not** invalidate `/users/5`.
- Fix: a byte budget (e.g. 50 MB), LRU eviction, honour request `no-cache`, and segment-aware invalidation.

### G6. The Express middleware swallows the first Ctrl+C / SIGTERM (Medium, DX)
- `packages/middleware/src/tunnel.ts:71-73` registers `process.once("SIGTERM"/"SIGINT", cleanup)`, and `cleanup` only stops the agent.
- Registering a signal listener **disables Node's default exit**. In a plain `node server.js` app the first Ctrl+C stops the tunnel and the server keeps running, so you have to press Ctrl+C twice.
- `docker stop` / Kubernetes / PM2 graceful reload hang until SIGKILL (10–30 s).
- Fix: after cleanup, re-raise if there are no other listeners (`if (process.listenerCount(sig) === 0) process.kill(process.pid, sig)`), or use `process.on('exit')` only.

### G7. The middleware turns the tunnel on anywhere `NODE_ENV` isn't `production` (Medium, security/DX)
- `middleware/src/config.ts`: `enabled = userConfig.enabled ?? NODE_ENV !== "production"`.
- Staging servers, CI runners, preview containers and Docker images often run with `NODE_ENV` unset or set to `staging`/`test`. If `VHYXVOID_API_KEY`/`SECRET` happen to be in that environment (copied `.env`), the server silently exposes itself on a public URL.
- `@vhyxvoid/next` is stricter (`NODE_ENV === 'development'`). Make the middleware match: opt-in only when `NODE_ENV === 'development'`, and require `enabled: true` otherwise. Also skip when `CI=true`.

### G8. The middleware can't know the app's real port (Medium, DX)
- The middleware defaults to port 3000 (`VHYXVOID_PORT` or 3000). It has no idea which port the Express/Fastify app actually listens on, so an app on :4000 gets 502s through the tunnel with no hint why.
- The middleware *is* in the request path, so it can detect the real port from the first request's `req.socket.localPort`. In Fastify it can read `fastify.server.address()` in an `onReady` hook.
- At minimum, log a loud warning when the backend refuses connections on the configured port.

### G9. Removing a member leaves their API keys active (High, access control)
- `RemoveMember.usecase.ts` deletes the membership row and nothing else. Keys the removed user created in that org (`ApiKey.createdById`) remain `ACTIVE`, and the hub doesn't check membership.
- A removed employee or contractor therefore keeps full tunnel access to the org: agent registration, SDK. Combined with first-pass H3, even revoking later doesn't kill a running agent.
- Pending invitations sent by the removed admin also stay valid.
- Fix: on removal (and on leaving), revoke or reassign that user's keys in the account (make it a UI choice: "revoke their 3 keys" vs "transfer to me"), cancel their pending invitations, and evict agents (see A3).

### G10. There's no account or user deletion path (Medium, compliance)
- `Account.deletedAt`/`User.deletedAt` and the `DELETED` status exist, but no use case or route deletes anything.
- `ApiKey.createdBy`/`revokedBy` have no `onDelete` rule, so a hard delete of a user who created keys is blocked by FK.
- GDPR/DPDP "delete my account" requests can't be served. This is also the reason `analyticsRetentionDays` has nothing to prune.

### G11. Notification types are defined but never sent (Low, product gap)
- `TUNNEL_DISCONNECTED`, `TRIAL_ENDING` and `SYSTEM_ALERT` exist in the enum and are never emitted.
- Stripe's `customer.subscription.trial_will_end` is received and ignored (`HandleStripeWebhook.usecase.ts:87`).
- These are cheap wins (see F6/F10).

### G12. One 10 MB JSON message blocks the whole hub (High, scalability)
- Every `tunnel:response` is `JSON.parse`d on the hub's single event loop. A 10 MB body as base64 is ~13 MB of JSON, and parsing plus `Buffer.from(base64)` costs tens of milliseconds per message.
- During that time **every tunnel for every customer** waits: head-of-line blocking.
- The hub has no worker threads and no streaming, so one customer serving large files degrades p99 latency for everyone.
- See A2 (binary frames and streaming) and A6 (per-tenant fairness).

### G13. Timeouts don't line up along the request path (Low)
| Hop | Timeout |
|---|---|
| SDK `createClient` | 30 s |
| agent → backend | hub timeout − 2 s (118 s) |
| hub pending | 120 s |
| nginx wildcard | 3600 s |
| Cloudflare (hub.) | ~100 s |

- A `createClient` caller gives up at 30 s while the hub and agent keep working on the request for another 90 s, with nothing to cancel it.
- There's no cancellation message (`tunnel:cancel`) in the protocol, so a client disconnect never stops the backend work either (see first-pass M14).
- Add `tunnel:cancel` and propagate `req.on('close')`.

### G14. The hub trusts `X-Forwarded-*` headers from the internet (Low)
- The tunnel nginx block appends to a client-supplied `X-Forwarded-For` (`$proxy_add_x_forwarded_for`), and the hub forwards it unchanged, so backends that trust the left-most XFF can be told any IP.
- Similarly `X-Forwarded-Proto` is passed through from the client if nginx doesn't overwrite it (it does set it in the wildcard block, which is fine).
- Fix: in the wildcard block, set `X-Forwarded-For $remote_addr` (overwrite, don't append), and document which headers the backend can trust.

## 2. Edge cases worth a test each

**Protocol and tunnel**
1. A request path containing `%2F`, `..`, `//`, a `#` fragment, or non-UTF-8 bytes. Check what reaches the backend and that `ResponseCache` keys stay distinct.
2. Duplicate request headers (`X-Forwarded-For` twice, two `Cookie` headers from HTTP/2 splitting). The hub casts `req.headers` to `Record<string,string>`, but `set-cookie` in requests and some duplicates arrive as arrays.
3. A response with **multiple** `Set-Cookie` headers where one value itself contains `\n` (malformed backend). The agent joins with `\n` and the hub splits on `\n`, so the framing is ambiguous. Use an array on the wire.
4. A `HEAD` request: the backend returns `content-length: N` and no body. Make sure nothing waits for N bytes (works today, but it's fragile together with H5's header fix).
5. `204`/`304` responses carrying a body or `content-length`.
6. A backend that sends `Transfer-Encoding: chunked` with trailers.
7. Server-Sent Events (`text/event-stream`), and long-poll responses longer than 120 s. Today the whole body is buffered by axios, so **SSE never works through the tunnel**: the client sees nothing until the stream ends or times out. This is a notable gap for dev tools (Next.js HMR falls back to it; many AI apps stream). See F3.
8. `Expect: 100-continue` uploads (curl sends this for bodies over 1 KB).
9. A WebSocket upgrade with `Sec-WebSocket-Protocol` (Vite HMR). Known D4, listed here for the test matrix.
10. A label reconnect storm: kill -9 the agent 50 times in a minute. Check the registry, subdomain key, plan-limit count and `tunnel_sessions` rows (see first-pass H7/M5).

**Accounts and billing**

11. The owner downgrades from PRO (5 agents, 10 members) to FREE (1/1). Existing agents stay connected (the limit is only checked at register), members stay, and keys over `maxApiKeys` stay usable. Decide and document grandfathering behaviour.
12. An invitation is accepted after the inviter's plan was downgraded (handled: `AcceptInvitation` re-checks). An invitation accepted after the **inviter was removed** is still valid (G9).
13. A user is a member of 20 orgs and switches between them quickly. Check query-cache key isolation per `accountId` in `apps/web`.
14. The Stripe webhook arrives before the checkout redirect returns (the UI should poll rather than assume).
15. The clock skew on a developer laptop is over 60 s. Every SDK signature fails with a timestamp error; the error should say "your clock is off by N s".

**Agent and integrations**

16. The local backend isn't started yet when `next dev` starts the agent. The first requests get 502s with the local port in the message (see first-pass M10).
17. Two `next dev` processes in one repo (monorepo). They register the same label, and each replaces the other on every reconnect (flapping). Known backlog item; needs a clear "label already in use by another machine" error instead.
18. A laptop sleeps for 8 hours and resumes. Reconnect backoff may be at 300 s, so the tunnel is dead for up to 5 min after wake. Reset the backoff on network-change events, or cap it at 30 s for the first attempts.
19. A corporate proxy (`HTTPS_PROXY` env). The agent's `ws` connection ignores proxy env vars, so the agent can't connect from many corporate networks. See F12.

## 3. Stress and load test plan

Run everything against a local stack (`docker compose` with nginx + hub + api + local Redis/Postgres) or a dedicated staging environment, **never** production.

### 3.1 Harness
- **Echo backend:** tiny Node server with `/echo`, `/bytes?n=`, `/gzip?n=`, `/slow?ms=`, `/sse`, and `/ws`.
- **Agent:** run 1 agent (CLI) plus N agents (a script spawning `AgentClient` instances with distinct labels on distinct accounts).
- **Load generator:** k6 (HTTP + WS) or autocannon, run from a separate machine.
- **Observability:** hub heap/RSS, event-loop lag (`perf_hooks.monitorEventLoopDelay`), pending-registry size, Redis commands/s (Upstash dashboard), Postgres connections and queries/s.

### 3.2 Scenarios and pass criteria

### 3.3 Capacity questions the tests should answer
- The hub's maximum sustained rps and MB/s on the current VM before event-loop lag exceeds 50 ms.
- Heap per connected idle agent, per in-flight 1 MB request, and per open tunnel WS. From these, the number of FREE users one hub can hold.
- Upstash commands per 1,000 SDK requests and per 1,000 public requests, turned into a monthly cost per active user. This decides whether the public-path design (in-process counting) should also be used for the SDK path.

## 4. Architecture and efficiency improvements

### A1. Data plane: separate the hub into an edge router and a control connection
Today one Node process does TLS-terminated HTTP intake (behind nginx), agent WebSockets, JSON parsing of every body, auth, rate limiting and bookkeeping.
- **Short term:** move the per-request hot path off JSON (A2) and offload the big `JSON.parse`/base64 work to a `worker_threads` pool, or skip it via streaming.
- **Medium term:** run the hub as N processes (Node cluster or several containers). Use **consistent routing by account** at nginx (`hash $host consistent` on the tunnel host) so an account's agent and its public traffic land on the same hub. That removes most of the need for `HubPubSub` cross-hub forwarding, and solves the per-instance limiter problem in the S5 backlog note.
- **Long term:** if throughput matters, the data plane is a good candidate for Go or Rust (as ngrok, frp and cloudflared are), keeping the control plane in TypeScript.

### A2. Binary framing with multiplexed streams
Replace `tunnel:forward/response` JSON+base64 with a small binary protocol over the existing WS: `[streamId][type][flags][len][payload]`, where the types are headers, data chunk, end, and cancel.
- Removes the +33% base64 overhead and roughly halves hub memory per request.
- Enables **streaming**: SSE, large downloads, uploads with no 10 MB cap, first-byte latency independent of body size.
- Enables **cancellation** when the browser disconnects (G13).
- Lets the WS relay reuse the same frames.
- Negotiate it with a capability flag in `agent:register` so old agents keep working (the protocol already carries `v`).
- Alternatively, adopt HTTP/2 over a single TLS connection from agent to hub (what cloudflared does) and get multiplexing and flow control for free.

### A3. A session model that survives short disconnects
- Key pending requests by **(account, label)**, as today, and do *not* reject them the moment the socket closes. Give a same-label reconnect a 5–10 s grace window to pick them up.
- Combined with idempotency keys for non-GET requests, this turns the accepted "inbound replay gap" (hub Known Risk #3) into a solved problem for the common Wi-Fi-blip case, and makes G3's outbound queue meaningful again.

### A4. Event-driven control → data plane
- The API should publish `key.revoked`, `key.rotated`, `member.removed`, `account.status_changed` and `plan.changed` events on Redis pub/sub. The hub subscribes and acts immediately: evict, re-read limits, drop cached plan.
- This replaces the 60 s status sweep, closes first-pass H3 and G9, and makes plan downgrades (§2 #11) take effect deterministically.
- The `HubPubSub` class already exists as the natural home for this.

### A5. Cheaper Redis usage
Per SDK request today: replay `SET NX`, key `GET` (cache), rate `INCR`+`EXPIRE`, usage `INCR`+`EXPIRE`, pending `SET`, pending `DEL`, which is about 8 REST round-trips.
- Remove the pending mirror (nothing reads it).
- Keep an **in-process LRU of API-key records** (~30 s TTL, invalidated by A4 events) instead of a Redis GET per request.
- Batch usage in-process, as `PublicPathUsageLimiter` already does.
- Combine replay and rate into one Lua script (`EVAL`).

Target: 1 Redis command per SDK request. At Upstash pay-per-request pricing this is roughly an 8× cost reduction. Alternatively, move to a TCP Redis (self-hosted or Upstash's TCP endpoint with `ioredis`), which also removes HTTPS round-trip latency (~5–20 ms per command today).

### A6. Per-tenant fairness
- Add per-account concurrency caps on the hub (in-flight requests and bytes in flight).
- Add a per-agent send queue with backpressure: check `ws.bufferedAmount` before sending, and pause reading the public request when an agent's socket is saturated.
- Without these, one tenant can monopolise the hub (S5).

### A7. Database hygiene
- **Retention.** `tunnel_requests`, `SecurityEvent`, `AuditLog` and `Session` (revoked rows) grow without bound, and `analyticsRetentionDays` isn't implemented. Add a nightly job using batched deletes by `createdAt`, or partition `tunnel_requests` by month and drop old partitions (much cheaper than deletes).
- **Write load.** Each SDK request does `TunnelRequest.create` (after a `findUnique` on the session) plus a later `updateMany`, which is 3 queries. Buffer audit rows in-process and `createMany` every 1–2 s, including the response status, so the update isn't needed.
- **Connection pooling.** Hub and API each open a Prisma pool against Neon. Use the `-pooler` endpoint (PgBouncer) for both, with an explicit `connection_limit`.
- **Indexes.** Drop the redundant `@@index` duplicates of `@unique` columns (first-pass L2). Add `(accountId, status, disconnectedAt)` for the history screen if it grows.

### A8. Configuration and secrets
- Validate the API's env at boot the way the hub already does for the pepper: one zod schema for all required variables, failing fast with a clear list.
- The server's `.env.production` files hold the Stripe secret, the RSA private key, the Redis token and the pepper in plain files. Move them to Docker secrets or a secrets manager, and document a rotation runbook per secret (the pepper is special: rotating it invalidates every API key, so it needs a dual-pepper verification window).

### A9. Deployment and release
- Deploys run `docker compose up` on a single VM, so every hub deploy drops every tunnel.
- Add graceful drain: on SIGTERM, send `hub:draining` to agents so they reconnect to the new container, while still serving in-flight requests. Run two hub containers behind nginx for a blue/green swap. This needs A1's account-affinity routing.
- Add a smoke test after deploy: an agent connects, a request goes through the tunnel, the response is checked. Roll back automatically on failure.
- Tag images with the git SHA (already done) and record the deployed SHA in `/health`.

### A10. Developer-experience architecture
- **Single source of defaults.** Labels (`default` vs `app`), ports, hub URL and env var names are repeated across `agent/cli.ts`, `middleware/config.ts`, `next/index.ts` and `sdk/client.ts`, and they already disagree (first-pass M24). Move them into `@vhyxvoid/protocol` constants or a tiny `@vhyxvoid/config` module.
- **One embeddable agent.** Replace the two framework wrappers with a single `startEmbeddedTunnel()` in the agent package. Its defaults would be in-memory only, no discovery, detected port and proper signal handling, which fixes G6, G7 and G8 in one place.

S is about 1–3 days, M about 1–2 weeks, L is multi-week.
